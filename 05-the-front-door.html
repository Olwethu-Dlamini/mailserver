Part 05 · The tools

The Front Door, Second Attempt: Cloudflare Instead of a VPS

The first version of this page designed a rented VPS running HAProxy and Postfix. It was never built. The budget for it was zero, so I went looking for a front door that costs nothing, and found one that works, with trade-offs I can name.

Rewritten on the afternoon of 8 October 2026, after the design below had carried its first real messages in both directions. The build steps are in part 08.

1. The constraint that changed, and what I checked before designing again

Part 01 ended with "something with a real public IP has to accept port 25 for me". The obvious something was a small rented VPS, about €4 to €5 a month, and the first draft of this page was that design: HAProxy in TCP mode passing 25, 465 and 993 over Tailscale to Stalwart at home, with a relay-only Postfix sending outbound from the VPS's clean IP.

Then the actual constraint arrived: there is no monthly budget for this, not even a coffee's worth. So before redesigning anything I made a list of every free thing that might do the job and checked each one, because "free alternative" is where projects usually go to die of wishful thinking.

Two measurements from srv1 settled the shape. Outbound port 25 is filtered by the ISP: a connection attempt to Gmail's MX gets no answer and Stalwart's own delivery attempt died with delivery.connect-error after 133 seconds. Outbound 587, 465 and 2525 all connect within a second. So sending through a relay on 465 is possible from home, and receiving has to be handed to something that accepts port 25 on my behalf.

2. Receiving: Email Routing, a Worker, and a TCP connection through my own tunnel

Cloudflare Email Routing is the free product that makes Cloudflare the MX for a domain. Normally it forwards each message to a mailbox elsewhere. It can also hand the message to an Email Worker, a small JavaScript function Cloudflare runs at its edge, with the raw message bytes as a stream.

On its own that was not enough: a Worker at Cloudflare's edge is still outside my house. What made it enough is Workers VPC. A Worker can declare a binding to a Cloudflare Tunnel in the same account, and then call connect("127.0.0.1:25") on that binding. The connection comes out of the cloudflared process already running on srv1, so 127.0.0.1 means srv1's own loopback, and port 25 is Stalwart. The tunnel I built for websites now also carries an SMTP session, in the one direction CGNAT allows: outbound from my VM, with the Worker's traffic riding back down it.

I did not write the Worker. A project called email-smtp-bridge on GitHub does exactly this, about a hundred lines, AGPL, with "stalwart:25" in its sample config. I read every line, vendored it into this repo under worker/, and changed two values:

{
  "name": "mail-inbound-bridge",
  "main": "src/index.ts",
  "workers_dev": false,
  "compatibility_date": "2026-10-01",
  "vpc_networks": [
    { "binding": "VPC", "tunnel_id": "0cf125dc-378c-4af2-83e3-d58df0fbed3f" }
  ],
  "vars": { "SMTP_ADDRESS": "127.0.0.1:25" },
  "observability": { "enabled": true }
}

The handler in src/index.ts reads the whole message into memory, opens the VPC socket, and hands both to a small SMTP client in src/smtp.ts. That client does the conversation from part 02 and nothing more: wait for 220, EHLO, MAIL FROM with the envelope sender Cloudflare received, RCPT TO with my address, DATA, the bytes with dot-stuffing applied (any line beginning with a dot gets a second dot, then CRLF . CRLF ends the message), wait for 250, QUIT. Two error classes decide what Cloudflare tells the original sender: a 5xx reply from Stalwart becomes message.setReject(), so the sender gets a bounce; anything else is thrown, which makes Cloudflare retry later. One comment in that file is worth repeating because it bit the author: Workers VPC does not fail connect() for an unreachable host, the stream simply ends, so a missing banner is treated as a temporary error.

The important property is that the bytes are unchanged. Stalwart receives the exact message Gmail sent, with Gmail's DKIM signature intact, so it runs its full inbound pipeline: DKIM verification, DMARC evaluation, the spam classifier, Sieve rules, delivery. The one thing it cannot do is judge the connecting IP, because the connection comes from loopback. That shows up in the log as smtp.spf-ehlo-fail and smtp.spf-from-fail with a soft fail, and it did not change the verdict: Gmail's message passed DKIM, passed DMARC on the strength of it, and was filed as ham. Cloudflare has already done the IP-level checks at its edge before the Worker ever runs.

Beta, and a two-commit project

Workers VPC is in beta and "free to all Workers plans while in beta". The Worker is vendored from a repository with two commits. Both facts are fine for a personal mailbox and would not be fine for a company's. The fallback if either changes is in section 5: the same Worker shape, but posting the message over HTTPS to a tiny receiver behind the tunnel, which several older projects already do.

3. Sending: a relay route to Resend

Stalwart has a Relay Host route type: instead of looking up the recipient's MX and connecting on port 25, deliver everything to one named server with a login. The route points at smtp.resend.com, port 465, implicit TLS, username resend, and an API key as the password. Resend then delivers to the real MX from its own IPs, which have the reverse DNS and reputation my ISP's shared address never will.

A route on its own does nothing; the outbound strategy decides which route each recipient gets. The default expression sends local domains to local and everything else to mx. One word changes:

Routing:
  IF   is_local_domain(rcpt_domain)   THEN 'local'
  ELSE 'resend'

Mail between my own accounts still never leaves the VM. Everything else goes to Resend. Neither the route nor the strategy takes effect until Management › Actions › Reload › Server settings is run, which I learned by watching a test message head for Gmail's port 25 and time out twice before I found that button.

Why DMARC still passes when a third party sends

Part 03 said DMARC needs the From: domain to align with either SPF or DKIM. Resend publishes two records for the domain: a DKIM key at resend._domainkey, and a CNAME rsend pointing at its SPF host. Resend signs every message it relays for me with that key, d=22112002.xyz, so DKIM aligns regardless of which IP the message leaves from. Stalwart also signs with its own keys before handing over, so the message carries two valid signatures for the same domain. SPF at the apex is Cloudflare's (v=spf1 include:_spf.mx.cloudflare.net ~all), which covers Email Routing's forwarding; Resend's SPF lives on its own subdomain and does not need to be in the apex record. The _dmarc policy stays mine, still p=reject from the morning, which is stricter than I wanted and is on the list to lower to none.

What this costs in messages, not money

Resend's free plan is 3,000 messages a month and 100 a day, sending pauses rather than charging at the cap. For a personal address that is a ceiling I will not see. If it ever bites, the strategy expression can route a second relay by domain or by sender in the same IF/THEN editor.

4. Reading on a phone without a VPN

The VPS design would have exposed real IMAP on 993. Without it, the obvious answer is "put the phone on Tailscale", which I rejected: I do not want a VPN app on the phone for this. The answer that costs nothing and needs no app beyond a mail client is JMAP.

JMAP is mail over HTTPS, and Stalwart speaks it natively (part 04). HTTPS is the one thing the Cloudflare Tunnel was built to carry. So mail.22112002.xyz became a tunnel hostname like every website, with Caddy in front of Stalwart's HTTP port:

# Stalwart over the tunnel: JMAP, autoconfig, MTA-STS policy, account page.
# The admin console is NOT exposed here; it stays on Tailscale.
mail.22112002.xyz:80, mta-sts.22112002.xyz:80, autoconfig.22112002.xyz:80, autodiscover.22112002.xyz:80 {
	@admin path /admin /admin/*
	respond @admin 403
	reverse_proxy 127.0.0.1:8080
}

Plus one line in /etc/stalwart/stalwart.env, STALWART_PUBLIC_URL=https://mail.22112002.xyz, so the URLs Stalwart hands to JMAP clients point at the public name. From the internet, https://mail.22112002.xyz/.well-known/jmap answers with a 307 to the session endpoint, which returns the server's capabilities, and /admin returns 403. The same block publishes the autoconfig XML that desktop clients use and the MTA-STS policy, for free.

Phone apps that speak JMAP: Twake Mail (Android and iOS), Sterna Mail (Android, open source, tested against Stalwart by its author), Ltt.rs (Android). Each asks for the server address and the account password, nothing else. Roundcube at webmail.22112002.xyz stays as the browser option, and it already works on a phone screen.

Not yet tested

The JMAP endpoint answered correctly from the public internet on the day of the build, but I had not yet logged in from a phone app when this was written. The first Twake Mail login goes in the build log when it happens.

5. Roads not taken, and the one kept in reserve

The rented VPS: HAProxy inbound, Postfix outbound, over Tailscale

This was the whole first version of this page: a €4 to €5 a month box with a public IP and an editable PTR record, HAProxy in TCP mode passing 25, 465 and 993 to Stalwart at home with the PROXY protocol so the spam filter sees the real client IP, and a relay-only Postfix bound to the Tailscale interface so outbound mail leaves from the VPS. It is the better design on every technical axis: real IMAP from anywhere, the sender IP visible to Stalwart, no third party reading outbound mail, no beta feature. It lost on the only axis that was fixed: it costs money every month. If a budget ever appears, the design still stands and the earlier draft of this page is in the repo's history.

The HTTPS gateway, kept as the fallback

Before Workers VPC existed, the way to get an Email Worker's message home was to fetch() it as an HTTPS POST to a hostname behind the tunnel, where a small receiver checks a shared secret and injects the bytes into the mail server over SMTP on loopback. Two projects on GitHub do this (one called mailbridge, written for Mailcow). It needs one more moving part on srv1 than the VPC route, but depends on nothing in beta. If Workers VPC changes its terms, the Worker handler changes by a dozen lines and the receiver is a short script behind one more Caddy block.

Forwarding to Gmail and reading it there

Email Routing could forward a copy to Gmail and Gmail's "Send as" could send through Resend. Free, no app, but Google has announced the end of "Send as" for third-party addresses in January 2027, and the mailbox would live at Google, which defeats the point.

Stalwart's own HTTPS fetch of the message

I briefly considered having the Worker store messages somewhere Stalwart could poll. It adds a store, a poller and a delay for no benefit over a live SMTP session through the tunnel.

6. What this design costs instead of money

  • Two outside dependencies for the two things my house cannot do. Cloudflare receives, Resend sends. Either going away or changing its free plan means rework, though in both cases the replacement is the same shape with a different name.
  • Stalwart never sees the sending server's IP. Every inbound connection is from loopback, so IP reputation lists and SPF are evaluated against 127.0.0.1 and soft-fail. DKIM and DMARC still work on the content, and Cloudflare applies its own IP checks before the Worker runs. For a personal mailbox this has been enough; it would matter for a server receiving at volume.
  • No public IMAP or submission. Ports 465 and 993 exist only on loopback for Roundcube. Phones use JMAP over HTTPS or Roundcube. Thunderbird users would need JMAP support or Tailscale.
  • A beta feature in the critical path. Workers VPC. The fallback above exists for a reason.
  • Vendored upstream code. The Worker in worker/ is a copy of a two-commit project. It is small enough to own; I read all of it, and the repo is where fixes go.
  • Outbound mail passes through Resend in the clear to them. TLS protects it on the wire; Resend itself sees every message it relays. The VPS design avoided this.

Against all of that: the design was built in an afternoon, needs no port open anywhere, no new machine, no monthly bill, and both directions carried real mail to and from Gmail on the first day. Part 08 is the record of that afternoon.

Glossary for this part

Email Routing
Cloudflare's free inbound mail product. It makes Cloudflare the MX for the domain and forwards each message to an address, or hands it to a Worker.
Email Worker
A Cloudflare Worker with an email(message, env, ctx) handler. It receives the envelope addresses, the headers and the raw message as a stream, and can forward, reject, or do anything else JavaScript can do.
Workers VPC
A binding that lets a Worker reach private hosts through a Cloudflare Tunnel, Mesh or WAN on-ramp in the same account, over HTTP with fetch() or raw TCP with connect(). Beta, free on all plans while it is.
Relay Host route
Stalwart's route type that delivers to one fixed server with optional authentication instead of resolving the recipient's MX.
Outbound strategy
Stalwart's expression that picks a route, schedule, connection and TLS strategy per recipient at delivery time. Changes need a settings reload.
Dot-stuffing
SMTP's rule that a line in the message body beginning with a dot gets an extra dot, so the lone-dot line that ends DATA cannot be forged by content.
JMAP
Mail over HTTPS and JSON. The protocol a tunnel can carry, which is why it is the phone answer here.
Alignment
DMARC's requirement that the visible From domain match the domain SPF or DKIM authenticated. Resend's DKIM key for my domain is what keeps relayed mail aligned.
