Part 05 · The tools

The Front Door: A Relay VPS Over Tailscale

Part 01 ended with a constraint: some machine with a real public IP has to accept port 25 for me, and outbound mail has to leave from an IP whose reputation is mine. This part designs that machine to do as little as possible.

Design only. The commands to build it are in part 08. Tailscale addresses shown are mine; <vps-tailscale-ip> and <vps-public-ip> are placeholders until the box exists.

1. The job description

The rented box has exactly two jobs, and I want it to have no others:

  1. Inbound: accept TCP connections from the internet on ports 25, 465 and 993, and hand each one, byte for byte, to Stalwart on srv1 over Tailscale, while telling Stalwart who the real client was.
  2. Outbound: accept messages from Stalwart over Tailscale and deliver them to the rest of the internet, so that Gmail sees the VPS's IP, its PTR record and its HELO name, all of which I control.

It stores no mail. It holds no mailbox passwords. It does not terminate TLS for IMAP or submission, so it never sees a user's password or message in the clear. It does not run a spam filter. If it is wiped tomorrow, I rent another one, re-run part 08, and change one A record. That is the test I kept applying to each design decision: could this box be replaced in an hour with nothing lost?

2. Choosing a provider: two questions, then price

The requirements list is short, and the first two items disqualify most of the big names.

RequirementWhy
Port 25 open, inbound and outboundWithout inbound 25 nothing can deliver to me. Without outbound 25 the relay cannot deliver to anyone. Many providers block one or both on new accounts to stop spammers.
PTR (reverse DNS) editableReceivers check that the connecting IP's PTR names a host that resolves back to the same IP. If I cannot set it to mail.22112002.xyz, I fail that check on every message.
A dedicated IPv4 addressPlenty of mail servers still have no IPv6. A shared or NAT'd IPv4 is useless here for the same reasons as CGNAT at home.
CheapHAProxy and a relay-only Postfix need almost nothing. The smallest plan is fine.
Any regionMail is store-and-forward. A few hundred milliseconds between Eswatini and Europe is invisible.

What I found when I checked the providers people usually name, as of writing. Policies change, so ask the two questions before paying:

  • Hetzner: blocks port 25 on new accounts. You open a support ticket after the first invoice is paid and explain what you are doing; they generally unblock it. PTR is editable in the console. About €4 to €5 a month for the smallest box.
  • Contabo, OVH: port 25 open by default, PTR editable. Similar price bracket.
  • DigitalOcean: blocks port 25 for new accounts and does not offer an unblock path. Not usable for this.
  • Oracle Cloud, AWS, GCP: port 25 blocked, with unblock processes that are slow, conditional or absent. The free tiers are tempting and a poor fit.
  • South African providers: several exist and would be closer. I have not verified their port 25 and PTR policies; the two questions above are the ones to ask their support before paying.
Ask before you pay

"Is TCP port 25 open inbound and outbound on your VPS plans, and can I set the reverse DNS of my IP myself?" If either answer is no or vague, move on. Everything else about the provider is secondary.

3. Inbound: HAProxy, TCP mode, PROXY protocol

HAProxy is a load balancer and proxy that can work at two levels. In HTTP mode it understands requests, like Caddy. In TCP mode it understands nothing about the protocol: it accepts a connection on one side, opens a connection on the other, and copies bytes between them. That is exactly what I want. SMTP, IMAP and their TLS handshakes pass through untouched. Stalwart at home still holds the certificates, still terminates TLS, still sees the user's password. The VPS sees ciphertext.

The one thing plain byte-copying loses is the client's address. From Stalwart's point of view every connection would arrive from the VPS's Tailscale IP, which would break SPF evaluation, DNSBL lookups, greylisting, rate limiting and auto-ban all at once. HAProxy fixes this with the PROXY protocol: before copying any bytes, it sends a short header to the backend saying "original client 209.85.220.41, port 51234, destined for your port 25". Stalwart reads that header, as long as it comes from an address in its trusted list, and then behaves exactly as if Gmail had connected directly.

Stalwart accepts PROXY protocol versions 1 and 2. HAProxy's send-proxy-v2 sends the binary version 2, which also carries TLS information. On the Stalwart side the trust is set per listener with overrideProxyTrustedNetworks on the NetworkListener (or globally with proxyTrustedNetworks under Settings › Network › General). I use the per-listener form so that only the listeners bound on the Tailscale address expect a header, and the loopback listeners Roundcube uses do not. A listener cannot decode both a PROXY header and X-Forwarded-For on the same connection, which does not matter here because nothing HTTP goes through this path.

The HAProxy configuration

This is the whole file. Three frontends on the public address, three backends to the same Tailscale address at home, PROXY protocol on every backend. Port 587 is commented out: 465 with implicit TLS is what modern clients prefer, and one fewer open port is one fewer thing to explain.

# /etc/haproxy/haproxy.cfg on the VPS
global
    log /dev/log local0
    maxconn 2000
    user haproxy
    group haproxy
    daemon

defaults
    mode tcp
    log global
    option tcplog
    option dontlognull
    timeout connect 10s
    timeout client  5m
    timeout server  5m

# ---- inbound mail from other servers ----
frontend ft_smtp
    bind <vps-public-ip>:25
    default_backend bk_smtp

backend bk_smtp
    server srv1 100.72.72.58:25 send-proxy-v2 check

# ---- my own clients: submission over implicit TLS ----
frontend ft_smtps
    bind <vps-public-ip>:465
    default_backend bk_smtps

backend bk_smtps
    server srv1 100.72.72.58:465 send-proxy-v2 check

# ---- my own clients: IMAP over implicit TLS ----
frontend ft_imaps
    bind <vps-public-ip>:993
    default_backend bk_imaps

backend bk_imaps
    server srv1 100.72.72.58:993 send-proxy-v2 check

# Optional: STARTTLS submission for older clients.
# frontend ft_submission
#     bind <vps-public-ip>:587
#     default_backend bk_submission
# backend bk_submission
#     server srv1 100.72.72.58:587 send-proxy-v2 check

Notes on the choices:

  • Five-minute client and server timeouts. SMTP sessions can legitimately idle while a server does DNS lookups and spam checks. The default one-minute timeouts in distro configs cut off slow but honest senders.
  • check makes HAProxy probe srv1 and log when it is unreachable, which is how I will find out that the Tailscale link or Stalwart is down before anyone tells me.
  • Binding to the public IP explicitly, not *, so HAProxy never listens on the Tailscale interface where Postfix lives.
  • Why HAProxy and not Caddy, given Caddy runs the rest of the homelab: Caddy's layer-4 proxying is a third-party plugin and a custom build. HAProxy in TCP mode is a one-package install with the PROXY protocol as a native feature, because HAProxy invented it.

4. Outbound: a relay-only Postfix on the Tailscale interface

Inbound is byte-copying. Outbound is not, because Stalwart at home needs to hand a message to something that will do the MX lookup and the delivery from the VPS's address. The smallest tool for "accept mail from one trusted host and deliver it onward" is Postfix with almost everything turned off. It listens only on the VPS's Tailscale address, accepts mail only from srv1's Tailscale address, and relays it to the world.

The Postfix configuration

These are the settings that matter in /etc/postfix/main.cf. Everything not listed stays at the Debian default.

# Identity: must match the PTR record and the A record
myhostname = mail.22112002.xyz
smtp_helo_name = mail.22112002.xyz

# Listen ONLY on the Tailscale address and loopback. Never on the public IP.
inet_interfaces = <vps-tailscale-ip>, 127.0.0.1
inet_protocols = ipv4

# Who may relay through this box: loopback and srv1's Tailscale address. Nothing else.
mynetworks = 127.0.0.0/8, 100.72.72.58/32
smtpd_relay_restrictions = permit_mynetworks, reject_unauth_destination

# This box delivers mail for NO domain of its own. Everything is relayed onward.
mydestination =
local_recipient_maps =
relayhost =

# Outbound TLS: use it when the other side offers it
smtp_tls_security_level = may
smtp_tls_loglevel = 1

# Inbound from srv1 may be plain; it is inside the Tailscale tunnel
smtpd_tls_security_level = none

# Keep the queue honest if the VPS cannot reach a recipient for a while
maximal_queue_lifetime = 3d
bounce_queue_lifetime = 1d
  • mydestination is empty so Postfix never thinks a message is "for this machine" and tries to deliver to a local Unix user. Every message goes out.
  • relayhost is empty because this Postfix is the last hop before the internet. It does its own MX lookups.
  • Plaintext between Stalwart and Postfix is acceptable because that hop is entirely inside Tailscale, which is WireGuard. Adding TLS there would mean a certificate for a Tailscale-only name and gain nothing. If I ever move the relay off Tailscale, this line changes first.
  • DKIM is signed at home. Postfix does not touch the body or the signed headers, so the signature survives. SPF passes because the connecting IP is the VPS and the SPF record says "whatever my MX points at", which is the VPS. DMARC then passes on both counts.
This must never become an open relay

An open relay is a mail server that will forward mail from anyone to anyone. Spammers scan for them constantly, and within hours of finding one they will push thousands of messages through it. The VPS's IP would be blacklisted everywhere, and my domain with it, before I noticed. Three settings prevent it and all three have to hold: inet_interfaces keeps Postfix off the public interface entirely, so nobody outside Tailscale can even connect; mynetworks lists only srv1; and smtpd_relay_restrictions rejects relaying from anything not in mynetworks. The test, from a machine that is not on my Tailscale network: nc -vz <vps-public-ip> 25 must connect (that is HAProxy) but openssl s_client -connect <vps-public-ip>:25 -starttls smtp must show Stalwart's banner, not Postfix's, and an attempt to send to an outside address without logging in must be refused with a 5xx. Part 09 has the full procedure, and MXToolbox's open relay test is the external confirmation.

The Stalwart side

In Settings › MTA › Outbound › Routes, one route of variant Relay:

{
  "@type": "Relay",
  "name": "vps-relay",
  "address": "<vps-tailscale-ip>",
  "port": 25,
  "protocol": "smtp",
  "implicitTls": false,
  "allowInvalidCerts": false,
  "authSecret": {"@type": "None"}
}

No authentication, because the only thing that can reach Postfix on that address is already srv1; Tailscale is the authentication. Then the outbound strategy has to select this route for every recipient that is not one of my own domains.

Verify during the build

The documentation describes the route being chosen by an expression on the MtaOutboundStrategy object, with examples that branch on recipient domain or authentication status. I have not seen the exact expression syntax for "any recipient not in a local domain → vps-relay". Part 08 records what the WebUI actually presents and what I typed.

5. The VPS firewall

A rented box with a public IP gets scanned within minutes of booting. The rule set is short because the box does so little:

PortFromWhy
22/tcpTailscale only, ideallySSH. Once Tailscale is up I connect via the Tailscale address and close 22 on the public side. Keep it public only until Tailscale is confirmed working.
25/tcpAnywhereHAProxy, inbound mail from other servers
465/tcp, 993/tcpAnywhereHAProxy, my own clients
41641/udpAnywhereTailscale's WireGuard port, so the VPS and srv1 connect directly instead of via a relay
Everything elseDroppedIncluding Postfix, which is not on the public interface at all

Debian's nftables or ufw both do this in a few lines; part 08 has the file. The important check afterwards is from outside: an nmap or a port checker against the public IP should show exactly 25, 465, 993 and whatever SSH state I have chosen, and nothing on 587 or 143 unless I enable them.

6. Roads not taken

Road not taken · nftables DNAT port forwarding

For it: no HAProxy process at all, just kernel rules that rewrite packets for port 25 to srv1's Tailscale address. Simplest possible front door. Against it: for the reply packets to find their way back through the VPS, either srv1 needs policy routing that sends its mail traffic back via the VPS, or the VPS has to masquerade, rewriting the source to its own address. Masquerading destroys the client IP, and unlike HAProxy there is no PROXY header to carry it, so SPF, DNSBL and rate limiting all break. Policy routing at home means touching srv1's routing table, which the Cloudflare tunnel and Tailscale also depend on. HAProxy costs one package and keeps the kernel out of it.

Road not taken · a Tailscale exit node

For it: one command on each side and srv1's outbound traffic would leave from the VPS's IP, no Postfix needed. Against it: an exit node routes all of srv1's traffic through the VPS, including the Cloudflare tunnel, package updates and every website's outbound calls. The blast radius is wrong: a problem with the VPS would take the websites down. It also does nothing for inbound. The relay-only Postfix sends exactly one kind of traffic through the VPS and nothing else.

Road not taken · a full MX on the VPS forwarding home over LMTP

For it: this is the textbook "backup MX" or "edge MX" pattern, with Postfix or a second Stalwart on the VPS accepting mail, filtering it and forwarding to home. It works and is widely used. Against it: the spam filter and the queue now live in two places, half the configuration moves off srv1, and when Tailscale is down my mail queues on the VPS disk instead of being retried by the sender. The byte-copying design keeps the VPS stateless: if the link is down, HAProxy refuses the connection and the sending server retries later, which is what SMTP was built for.

Road not taken · plain WireGuard instead of Tailscale

For it: the VPS has a public IP, so hand-configured WireGuard is finally possible here where it was not at home, and it would remove a third party. Against it: srv1 already runs Tailscale, MagicDNS gives me names, and NAT traversal from behind CGNAT to the VPS is handled for me. One more WireGuard config to maintain on a box I want to be replaceable in an hour is the wrong trade. If Tailscale ever becomes a problem this is the fallback, and the Postfix and HAProxy configs would only need the addresses changed.

Road not taken · Cloudflare Spectrum, ngrok and friends

Covered in part 01: Spectrum is Enterprise-only, and any shared TCP tunnel service gives me an IP whose reverse DNS and reputation belong to someone else. The whole point of the VPS is that its IP is mine.

7. The design on one line each

  • Inbound: HAProxy in TCP mode on the public IP, ports 25/465/993, send-proxy-v2 to Stalwart on 100.72.72.58; Stalwart trusts the VPS's Tailscale IP and sees the real client.
  • Outbound: Stalwart signs DKIM, routes to a Relay at the VPS's Tailscale IP; Postfix there, bound to Tailscale only, delivers to the world from the VPS's IP.
  • DNS: mail.22112002.xyz A → VPS (grey cloud), MX → mail.22112002.xyz, PTR of the VPS → mail.22112002.xyz, SPF v=spf1 mx -all; everything else published by Stalwart.
  • State on the VPS: none worth keeping. Replaceable in an hour.

Glossary for this part

TCP mode (HAProxy)
Layer-4 proxying: HAProxy copies bytes between two connections without understanding the protocol inside them. TLS passes through intact.
PROXY protocol
A header HAProxy sends at the start of a forwarded connection carrying the original client's address and port, so the backend can act as if the client connected directly. Version 2 is binary and also carries TLS details.
Smarthost / relay host
A mail server that accepts messages from a trusted source and delivers them onward. Here, the Postfix on the VPS.
Open relay
A smarthost that trusts everyone. The fastest way to get an IP blacklisted. Prevented by inet_interfaces, mynetworks and smtpd_relay_restrictions together.
HELO / EHLO name
The hostname a sending server announces at the start of an SMTP session. Receivers check that it resolves and matches the PTR record.
PTR record
Reverse DNS: the name an IP claims. Set at the VPS provider, not in Cloudflare.
Grey cloud
Cloudflare's "DNS only" setting for a record. Mail records must be grey; a proxied (orange) A record would point at Cloudflare's HTTP edge, which does not speak SMTP.
Exit node
A Tailscale device that other devices route all their internet traffic through. Too broad for this job.
