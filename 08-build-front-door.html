Build Part 2: The Free Front Door, As Built

Part 07 ended at lunchtime with a mail server that could only talk to itself. By six in the evening it had received a message from Gmail and sent one back, without a VPS, without a port open at home, and without a bill. This is what happened in between, in order, with the evidence.

Written after the build on 8 October 2026 from the build log in notes/. The earlier version of this page, a plan for a rented VPS, was never executed; part 05 explains why.
Written afterwards

Everything on this page was done. Where a step went wrong first, the wrong turn is kept. Times are South African time unless marked UTC, which is what Stalwart's log uses.

1. JMAP, autoconfig and MTA-STS through the tunnel (14:40)

First the part that did not depend on anyone else's account: publishing Stalwart's HTTP side the same way every website is published. One env line, one Caddy block, four tunnel routes.

echo 'STALWART_PUBLIC_URL=https://mail.22112002.xyz' | sudo tee -a /etc/stalwart/stalwart.env
sudo systemctl restart stalwart
# appended to /etc/caddy/Caddyfile
mail.22112002.xyz:80, mta-sts.22112002.xyz:80, autoconfig.22112002.xyz:80, autodiscover.22112002.xyz:80 {
	@admin path /admin /admin/*
	respond @admin 403
	reverse_proxy 127.0.0.1:8080
}
sudo caddy validate --config /etc/caddy/Caddyfile && sudo systemctl reload caddy
for h in mail mta-sts autoconfig autodiscover; do
  cloudflared tunnel route dns --overwrite-dns 0cf125dc-378c-4af2-83e3-d58df0fbed3f $h.22112002.xyz
done
# four ingress lines added above the http_status:404 catch-all, then:
sudo systemctl restart cloudflared

--overwrite-dns mattered: Stalwart's automatic DNS had already created mta-sts, autoconfig and autodiscover as CNAMEs to mail.22112002.xyz, and the tunnel route replaced them with proxied tunnel records. Stalwart did not put them back during the day.

Checkpoint · from the laptop, over the public internet
  • https://mail.22112002.xyz/.well-known/jmap → 307 to /jmap/session, which returned 200 with the JMAP capabilities JSON
  • https://mail.22112002.xyz/admin → 403
  • https://mta-sts.22112002.xyz/.well-known/mta-sts.txt → 200, mode: testing
  • https://autoconfig.22112002.xyz/mail/config-v1.1.xml?emailaddress=olwethu@22112002.xyz → 200, the client-config XML

One thing I noted and left: the MTA-STS policy says mx: mail.22112002.xyz, generated by Stalwart from its own idea of the MX. Once Cloudflare owns the MX that line is wrong. In testing mode a wrong policy does no harm, and the _mta-sts TXT was removed later in the afternoon anyway, so senders no longer look for it.

4. Handing the MX and SPF to Cloudflare (15:10 to 15:35)

Stalwart had been managing MX, SPF and MTA-STS all morning. Cloudflare Email Routing wants to own the MX and the apex SPF. So: in the Stalwart admin, Management › Domains › Domains › 22112002.xyz › DNS › Record Types, untick MX records, SPF records and MTA-STS policy record, Save.

Unticking does not delete anything. The records Stalwart had published stayed in the zone and had to be removed by hand on the Cloudflare DNS page. That took two passes: the first "done" had removed only the _mta-sts TXT, and the MX and the v=spf1 mx -all TXT were still answering five minutes later, which I confirmed by polling the resolver rather than assuming a cache.

A side effect I had been seeing since the morning finally made sense here. Once mail.22112002.xyz became a proxied tunnel record, Cloudflare rewrote the MX target to _dc-mx.0278da436451.22112002.xyz, a DNS-only alias that resolves to the tunnel's cfargotunnel.com name. A test message sent from Gmail during that window went to that name, found nothing speaking SMTP, and sat in Gmail's retry queue; Stalwart's log showed no inbound connection at all.

Checkpoint · after the second pass
  • 22112002.xyz MX → none (before Email Routing added its own)
  • 22112002.xyz TXT → no v=spf1 mx -all
  • _mta-sts.22112002.xyz TXT → none

"No targets deployed" looked like a failure and is not: an Email Worker has no HTTP route. The Email Routing rule is what triggers it. The VPC binding resolved against my tunnel first time, with no extra setup on the tunnel side.

While that uploaded, I did on srv1 exactly what the Worker is about to do, so that if the real message failed I would know which half to blame:

python3 - <<'EOF'
import smtplib, email.utils, time
msg = f"""From: Loopback Test <someone@example.org>
To: olwethu@22112002.xyz
Subject: loopback SMTP test {time.strftime("%H:%M:%S")}
Date: {email.utils.formatdate()}
Message-ID: {email.utils.make_msgid(domain="example.org")}

This simulates the Email Worker handing a message to Stalwart on 127.0.0.1:25.
"""
s = smtplib.SMTP("127.0.0.1", 25, timeout=20)
s.ehlo("gmail.com")
print(s.sendmail("someone@example.org", ["olwethu@22112002.xyz"], msg))
s.quit()
EOF
Checkpoint · Stalwart log, 13:46 UTC

  • message-ingest.spam: filed as possible spam, which is the right verdict for an unsigned sender claiming someone else's domain

So Stalwart accepts port-25 submissions from loopback for its own domain without authentication, runs the checks, and files the result. The only question left was whether the Worker could reach that port.

8. The relay route and the strategy (16:46)

Settings › MTA › Outbound › Routes › Add, route type Relay Host: Address smtp.resend.com, Port 465, Protocol SMTP, Implicit TLS on, Allow Invalid Certs off, Username resend, Secret → "Secret value" → the API key, Name resend. Save.

Settings › MTA › Outbound › Strategy. The Routing expression is an IF/THEN/ELSE editor. It read IF is_local_domain(rcpt_domain) THEN 'local' ELSE 'mx'; the ELSE became 'resend', quotes included. Scheduling, Connection and TLS were left alone. Save.

Then the step the admin pages do not mention: nothing applies until Management › Actions › Reload › Server settings. Actions lives at the bottom of the Management sidebar, the one that starts with Dashboard and Directory, not the Settings sidebar. The reload leaves no line in the log, which is how I nearly missed that it had not happened.

Glossary for this part

Catch-all rule
Email Routing's rule for any address that no other rule matches. Pointing it at the Worker sends the whole domain's mail home.
wrangler
Cloudflare's command-line tool for Workers: login, deploy, tail logs.
VPC Network binding
The vpc_networks entry in wrangler.jsonc that attaches a tunnel to the Worker as env.VPC.
Reload server settings
The Stalwart action that compiles saved configuration into the running server. Routes and strategies do nothing until it runs.
_dc-mx
Cloudflare's automatic alias for an MX record whose target is a proxied name. It exists so the MX still resolves to something, even if that something cannot speak SMTP.
Soft fail
SPF's ~all result: the sending IP is not listed, treat with suspicion but do not reject. What loopback produces here on every inbound message.
