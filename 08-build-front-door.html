Build Part 2: The Front Door

Part 07 left me with a working mail server that only my own devices could reach over Tailscale. This part gives it a public IP: a rented VPS that does nothing except accept mail connections on behalf of srv1 and send my outbound mail from an address the rest of the internet will trust.

Two machines, two terminals open side by side. Expect two to three hours, most of it waiting for DNS and a support ticket.
Written before the build

This page is the plan, written down before I did it, the way I wish the other guides had started. Once the build is done I will come back and correct whatever turned out to be wrong, and keep the wrong turns in. If a step reads too cleanly, assume it has not been tested yet.

1. Choosing the VPS

There are exactly two things this machine must have, and most of the cheap-VPS market fails at least one of them:

  1. Port 25 open, inbound and outbound. Inbound so other mail servers can reach HAProxy. Outbound so Postfix can deliver to them. Many providers block 25 by default to stop spam from freshly created accounts, and some never unblock it.
  2. An editable PTR record. I need to set the reverse DNS of the public IP to mail.22112002.xyz myself, from the provider's console. If the provider has to do it by ticket, that is acceptable. If they will not do it at all, that provider is out.

Beyond that: a dedicated IPv4 address (not shared, not NAT), the smallest tier they sell, and a Debian 12 or 13 image. HAProxy, Postfix and Tailscale together idle at well under 200 MB, so RAM is irrelevant here.

Before paying

Send the provider's support two questions in one message: "Is outbound and inbound TCP port 25 allowed on your smallest VPS, and can I set the PTR record for its IPv4 address myself?" Their answer is the deciding fact. A provider that answers yes to both in writing has just saved me from the Oracle trap.

Checkpoint
  • A VPS exists with a dedicated public IPv4 address. I will call it <vps-public-ip> everywhere below.
  • Written confirmation (or a provider policy page) that port 25 is or will be open, and that PTR is editable.
  • Root or sudo login works over SSH.

2. First login, hardening, Tailscale, firewall

This box is going to sit on a public IP with ports open to the whole internet. The first fifteen minutes are the same as for any public server, and I am not skipping them because "it only runs HAProxy".

# As root on the fresh VPS
apt update && apt upgrade -y
adduser oll
usermod -aG sudo oll

# From the laptop: copy the SSH key, then log in as the new user and confirm sudo works
ssh-copy-id oll@<vps-public-ip>
ssh oll@<vps-public-ip> sudo -v

Once key login works, turn off passwords. Edit /etc/ssh/sshd_config (or a file under sshd_config.d/) so these two lines are set, then restart SSH while keeping the current session open and test a second login before closing the first.

PasswordAuthentication no
PermitRootLogin no
sudo sshd -t && sudo systemctl restart ssh

Then join the VPS to the Tailscale mesh. It is the same two commands as every other machine in the homelab, and the same account.

curl -fsSL https://tailscale.com/install.sh | sh
sudo tailscale up
tailscale ip -4        # note this: it is <vps-tailscale-ip> below
tailscale status       # srv1 (100.72.72.58) should be listed

From here on I SSH to the VPS over Tailscale, not over the public IP. That lets the firewall close public SSH entirely: the only things the internet can reach are the three mail ports.

I used ufw here because it reads well in a guide. It is a front-end to nftables; if you prefer writing /etc/nftables.conf directly, the rules are the same four ideas: allow mail ports on the public interface, allow Tailscale's UDP port, allow everything on tailscale0, drop the rest.

sudo apt install -y ufw
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow in on tailscale0            # SSH, Postfix, everything: Tailscale only
sudo ufw allow 41641/udp                   # Tailscale's own port, so it can connect directly
sudo ufw allow 25/tcp
sudo ufw allow 465/tcp
sudo ufw allow 993/tcp
# sudo ufw allow 587/tcp                   # optional: STARTTLS submission, I am using 465 only
sudo ufw enable
sudo ufw status verbose
Do this in the right order

Confirm ssh oll@<vps-tailscale-ip> works before enabling the firewall. Once ufw is on, public SSH is closed, and if Tailscale is not up you have locked yourself out and need the provider's web console.

Checkpoint
  • ssh oll@<vps-tailscale-ip> works; ssh oll@<vps-public-ip> now times out.
  • tailscale status on the VPS shows srv1; tailscale ping 100.72.72.58 gets a direct reply.
  • sudo ufw status lists 25, 465, 993, 41641/udp and tailscale0, nothing else.

3. The PTR record

This is the one record I could never set from home, and the single biggest reason the VPS exists. In the provider's console, find the reverse DNS (rDNS, PTR) setting for <vps-public-ip> and set it to mail.22112002.xyz, with the trailing dot if the form wants one.

dig -x <vps-public-ip> +short
# expected, after a few minutes:
# mail.22112002.xyz.

Reverse DNS is published by the provider's name servers, not by Cloudflare, so Cloudflare has nothing to do with this step. Some providers refuse to set a PTR until the forward A record (next step) already exists and points at the IP. If the console rejects it, do step 4 first and come back.

Checkpoint
  • dig -x <vps-public-ip> returns mail.22112002.xyz.

4. DNS on Cloudflare: the one record Stalwart does not write

In Part 07, Stalwart was given a Cloudflare API token and publishes the MX, SPF, DKIM, DMARC, MTA-STS, TLS-RPT, CAA and autoconfig records for the domain itself. The one thing it cannot know is the public IP of a machine it has never heard of, so the A record for the mail host is mine to add.

In the Cloudflare dashboard, DNS for 22112002.xyz: add A, name mail, content <vps-public-ip>, proxy status DNS only (the grey cloud, not the orange one).

Grey cloud, always

Every other record in this zone is proxied, because that is how the tunnel works. This one must not be. A proxied record resolves to Cloudflare's IPs, which only speak HTTP; a mail server connecting to port 25 there gets nothing. Cloudflare knows this and shows a warning if an MX target is proxied. Heed it.

Now the chain the rest of the world will follow should resolve end to end:

dig MX 22112002.xyz +short          # 10 mail.22112002.xyz.  (published by Stalwart)
dig A mail.22112002.xyz +short      # <vps-public-ip>        (just added)
dig -x <vps-public-ip> +short      # mail.22112002.xyz.     (step 3)

Forward and reverse now agree. That agreement is called forward-confirmed reverse DNS and it is one of the first things a receiving server checks about me, so it is worth seeing it with my own eyes before moving on.

Checkpoint
  • All three dig commands above return what the comments say, against @1.1.1.1 as well as the local resolver.
  • The mail record in the Cloudflare dashboard shows a grey cloud.

5. HAProxy: the inbound forwarder

HAProxy's job here is deliberately dumb. It accepts a TCP connection on a public port and opens an identical TCP connection to srv1 over Tailscale, copying bytes in both directions. It does not read the mail, does not terminate TLS, does not know what SMTP is. The one clever thing it does is prepend a PROXY protocol v2 header on the connection to Stalwart, carrying the real client's IP, so that Stalwart's spam filter, SPF checks and rate limits see Gmail's address rather than the VPS's.

sudo apt install -y haproxy
sudo cp /etc/haproxy/haproxy.cfg /etc/haproxy/haproxy.cfg.dist

Replace /etc/haproxy/haproxy.cfg with this:

global
    log /dev/log local0
    maxconn 2000
    user haproxy
    group haproxy
    daemon

defaults
    log     global
    mode    tcp
    option  tcplog
    option  dontlognull
    timeout connect 10s
    timeout client  5m
    timeout server  5m

# ---- SMTP, server to server -------------------------------------------
frontend ft_smtp
    bind <vps-public-ip>:25
    default_backend bk_smtp

backend bk_smtp
    server srv1 100.72.72.58:25 send-proxy-v2 check

# ---- Submission over implicit TLS, my own clients ----------------------
frontend ft_smtps
    bind <vps-public-ip>:465
    default_backend bk_smtps

backend bk_smtps
    server srv1 100.72.72.58:465 send-proxy-v2 check

# ---- IMAP over implicit TLS -------------------------------------------
frontend ft_imaps
    bind <vps-public-ip>:993
    default_backend bk_imaps

backend bk_imaps
    server srv1 100.72.72.58:993 send-proxy-v2 check

Three things about those timeouts. IMAP clients hold a connection open and idle for a long time, so five minutes is the minimum that will not cause phones to reconnect constantly. timeout connect is about the hop to srv1 over Tailscale, which should take milliseconds, so ten seconds is generous. And binding to <vps-public-ip> rather than * leaves the Tailscale interface free for Postfix to use port 25 in step 7.

Validate before restarting. This is the lesson from the Caddy debugging session in the Homelab series: a config checker that runs in a second is worth more than a restart that fails in a way you then have to investigate.

sudo haproxy -c -f /etc/haproxy/haproxy.cfg
# Configuration file is valid
sudo systemctl restart haproxy
sudo systemctl status haproxy --no-pager
sudo ss -tlnp | grep haproxy
Checkpoint
  • ss -tlnp on the VPS shows haproxy on <vps-public-ip>:25, :465 and :993.
  • journalctl -u haproxy has no DOWN lines for srv1. If it does, HAProxy cannot reach 100.72.72.58: check Tailscale on both ends first, then that Stalwart's listeners on srv1 are bound to the Tailscale IP (Part 07).

6. Stalwart: trust the PROXY header from the VPS

Stalwart will not believe a PROXY header from just anyone, because anyone who could send one could claim to be any IP they liked. It has to be told which addresses are allowed to speak for others. The setting is proxyTrustedNetworks server-wide, or overrideProxyTrustedNetworks on an individual listener, and the per-listener one replaces the server-wide list for that listener.

I want the override, not the global setting, because only the three Tailscale-bound listeners sit behind HAProxy. The loopback listeners that Roundcube uses (Part 06) must keep treating connections as ordinary.

In the WebUI, Settings › Network › Listeners: open each of the listeners bound to 100.72.72.58 (SMTP on 25, submissions on 465, IMAP on 993) and set its trusted proxy networks to the single entry <vps-tailscale-ip>. Save, then trigger a settings reload so the running listeners pick it up.

Verify on the live UI

The field names above come from the Stalwart 0.16 reference (NetworkListener.overrideProxyTrustedNetworks, SystemSettings.proxyTrustedNetworks). The exact label in the listener form and the location of the reload action may differ from this text. Use the global search box in the WebUI for "proxy" if it is not where I said.

Expected breakage

From this point on, those three listeners expect every connection from the VPS to begin with a PROXY header. The direct tests from Part 07, where the laptop connected straight to 100.72.72.58:993 over Tailscale, will now fail if the laptop's IP is in the trusted list (it is not), or succeed only because the laptop is untrusted and is treated as a normal client. Either way, the path that matters from now on is mail.22112002.xyz:993 through HAProxy, and that is what I test.

Checkpoint
  • From the laptop, on mobile data: openssl s_client -connect mail.22112002.xyz:993 -servername mail.22112002.xyz shows the Let's Encrypt certificate from Part 07 and an IMAP greeting.
  • In Stalwart's live view or journalctl -u stalwart, the connection is logged with the laptop's public IP, not <vps-tailscale-ip>. That line is the proof the PROXY header is being read.

7. Postfix: the outbound relay

Inbound is solved. Outbound needs the mirror image: mail from Stalwart has to leave the internet from <vps-public-ip>, so that the IP Gmail sees has the PTR I set and is not a residential address. HAProxy cannot do that; it forwards connections to somewhere, it does not originate SMTP sessions. Postfix can, and configured as a relay-only host it is about twenty lines.

sudo apt install -y postfix
# In the installer dialog pick "No configuration". We write main.cf by hand.
sudo mv /etc/postfix/main.cf /etc/postfix/main.cf.dist 2>/dev/null

/etc/postfix/main.cf:

# Identity. Must match the PTR and the A record exactly.
myhostname = mail.22112002.xyz
smtp_helo_name = $myhostname

# Listen only where srv1 can reach me: Tailscale and loopback. Never the public IP.
inet_interfaces = <vps-tailscale-ip>, 127.0.0.1
inet_protocols = ipv4

# This box delivers nothing locally. Every message is for somewhere else.
mydestination =
local_recipient_maps =
local_transport = error:local delivery disabled

# Who may relay through me: myself, and srv1. Nobody else.
mynetworks = 127.0.0.0/8 100.72.72.58/32
smtpd_relay_restrictions = permit_mynetworks, reject_unauth_destination

# Outbound TLS: use it when the other side offers it.
smtp_tls_security_level = may
smtp_tls_loglevel = 1

# One log file I can tail.
maillog_file = /var/log/postfix.log
sudo postfix check
sudo systemctl restart postfix
sudo ss -tlnp | grep master     # expect <vps-tailscale-ip>:25 and 127.0.0.1:25, nothing public
Open relay check, do it now

An open relay is a mail server that will send anyone's mail to anyone. Spammers find them in hours, and once a relay has been abused the IP's reputation is gone, which defeats the entire purpose of the VPS. Two lines guard against it here: inet_interfaces keeps Postfix off the public IP entirely, and mynetworks plus reject_unauth_destination means even a connection from inside Tailscale is refused unless it comes from srv1. Prove both:

# From the laptop, on mobile data. HAProxy owns public 25, so you should see Stalwart's
# banner (via srv1), never Postfix's. Postfix must not be reachable here at all.
nc -v <vps-public-ip> 25

# From srv1, over Tailscale: this one IS Postfix.
nc -v <vps-tailscale-ip> 25
# 220 mail.22112002.xyz ESMTP Postfix

# From the laptop over Tailscale (not in mynetworks): connect, then try to relay.
# Expect "454 4.7.1 ... Relay access denied" on the RCPT TO.
nc -v <vps-tailscale-ip> 25

Note that the two banners on port 25 are different programs. On the public IP it is Stalwart, reached through HAProxy. On the Tailscale IP it is Postfix. Same port, two listeners, two interfaces, which is exactly why step 5 bound HAProxy to the public address only.

Checkpoint
  • postfix check prints nothing.
  • Postfix is listening on <vps-tailscale-ip>:25 and 127.0.0.1:25 only.
  • A relay attempt from an address that is not 100.72.72.58 is refused with Relay access denied.

8. Stalwart: send everything remote through the relay

By default Stalwart delivers like any MTA: look up the recipient domain's MX and connect to it directly. From srv1 that would go out over my home connection, which is the thing Part 01 explained will not work. So I give it a route that points at Postfix instead, and tell its outbound strategy to use that route for every remote recipient.

In the WebUI, Settings › MTA › Outbound › Routes: add a route of type Relay with these values.

FieldValueWhy
namerelayWhat the strategy refers to.
address<vps-tailscale-ip>Postfix's Tailscale-side listener. The IP, not mail.22112002.xyz, which would resolve to the public IP and reach HAProxy instead.
port25Where Postfix listens.
protocolsmtpPostfix speaks SMTP, not LMTP.
implicitTlsfalsePlain connection, STARTTLS if offered. The wire is already WireGuard inside Tailscale, so this is encrypted regardless.
authSecretNonePostfix trusts srv1 by IP via mynetworks; no password needed.

The equivalent object, for anyone scripting this with the CLI instead of clicking:

{
  "@type": "Relay",
  "name": "relay",
  "address": "<vps-tailscale-ip>",
  "port": 25,
  "protocol": "smtp",
  "implicitTls": false,
  "allowInvalidCerts": false,
  "authSecret": {"@type": "None"}
}

Then Settings › MTA › Outbound › Strategies: the outbound strategy decides, per recipient, which route to use. Local domains must keep being delivered locally; everything else must pick relay.

Expression syntax to confirm on the UI

The strategy's route is chosen by an expression that can branch on things like whether the recipient domain is local. I know the shape (local stays local, otherwise relay) but not the exact expression text in 0.16, and I am not going to guess it in a guide. Read the form's inline help, or the expressions page in the docs, and write down what actually worked here.

Checkpoint
  • The route relay exists and points at <vps-tailscale-ip>:25.
  • Sending from one local account to another (Part 07's test) still works; that proves local delivery was not accidentally routed to Postfix, which would bounce it with local delivery disabled.

9. The first real message

Two terminals, one on each machine, before pressing send:

# srv1
sudo journalctl -u stalwart -f

# VPS
sudo tail -f /var/log/postfix.log

Then, in Roundcube, send a short message from me@22112002.xyz to a Gmail address I own. What I expect to see, in order: Stalwart accepts the submission, signs it with DKIM, queues it, connects to the relay. Postfix logs the connection from 100.72.72.58, then an outbound connection to a Google MX host, then status=sent (250 2.0.0 OK ...).

In Gmail, open the message, then the three-dot menu, then Show original. This page is the receiving side's verdict and it is worth reading slowly the first time:

  • SPF: PASS with IP <vps-public-ip>. The IP must be the VPS. If it is a residential address, the route in step 8 is not being used.
  • DKIM: PASS with domain 22112002.xyz. Signed at home by Stalwart, verified against the public key Stalwart published to Cloudflare.
  • DMARC: PASS, because at least one of the two above passed and aligned with the From domain.
  • In the raw headers, the topmost Received: line written by Google should name mail.22112002.xyz and <vps-public-ip>, which is the FCrDNS pair from step 4 doing its job.

Now reply from Gmail. This time watch HAProxy as well: sudo journalctl -u haproxy -f on the VPS logs a connection from one of Google's IPs to ft_smtp, handed to bk_smtp. A moment later Stalwart's log on srv1 shows the same Google IP as the client. That is the PROXY protocol working: without it, Stalwart would see <vps-tailscale-ip> and every SPF and DNSBL check it does on inbound mail would be checking the wrong address.

Checkpoint
  • Gmail's "Show original" shows SPF, DKIM and DMARC all PASS and the connecting IP is <vps-public-ip>.
  • A reply from Gmail lands in Roundcube, and Stalwart's log records Google's IP, not the VPS's.

10. Deliverability checks

Gmail passing is a good sign, not a certificate. Three external checkers, each for a different thing:

  • mail-tester.com gives a one-time address; send it a message from Roundcube with a real subject and a couple of sentences of real text, then read the score. Aim for 10/10. The deductions I expect to be chasing: a missing List-Unsubscribe header (ignore it for personal mail), a message body that is too short or looks like a test (write more), the IP not being in any of their reputation databases yet (only time fixes that), and anything about SPF or DKIM, which means going back to step 9.
  • mxtoolbox.com: run the MX lookup, the SMTP diagnostics on mail.22112002.xyz, and above all the blacklist check on <vps-public-ip>. A freshly rented IP can be on a list because of its previous tenant. If it is, request delisting from each list, or ask the provider for a different IP before building anything else on this one.
  • learndmarc.com: send it a message and it walks through the SPF, DKIM and DMARC evaluation step by step, showing exactly which record it fetched and what it concluded. The best tool I found for understanding a failure rather than just seeing one.
Checkpoint
  • mail-tester at or near 10/10, with any remaining deduction understood and written down.
  • <vps-public-ip> is on no blacklist MXToolbox checks.

12. The first week: DMARC, MTA-STS, and what to watch

DMARC rollout. Stalwart publishes the DMARC record; what matters is its policy. Start at p=none with a reporting address so that I receive aggregate reports for a week or two and can see every source sending as my domain. Only once those reports show nothing but the VPS do I move to p=quarantine and then p=reject. Jumping straight to reject on day one is how people lose mail from a forwarding path they forgot about.

MTA-STS. The DNS record Stalwart publishes tells other servers that a policy exists; the policy itself is a small text file that must be served over HTTPS at https://mta-sts.22112002.xyz/.well-known/mta-sts.txt, from a certificate valid for that name. This can go through the Cloudflare Tunnel, because it is plain HTTPS: add mta-sts.22112002.xyz to the tunnel ingress and the Caddyfile the same way as any other site, and either serve a static file or reverse_proxy to Stalwart's HTTP listener.

Verify

Stalwart's HTTP listener is documented as serving the MTA-STS policy for managed domains, which would make the Caddy block a two-line reverse proxy. I have not confirmed the exact path it serves it on. If it does not, the static-file version is a four-line policy I can write by hand, with mx: mail.22112002.xyz and mode: testing until the DMARC reports are clean.

What to watch for the first week:

  • /var/log/postfix.log on the VPS for status=deferred or status=bounced, especially from Outlook/Hotmail, which is slower than Gmail to trust a new IP.
  • Stalwart's queue page for anything stuck. A message that sits there for hours means the relay route or Postfix is unhappy.
  • The DMARC aggregate reports (Stalwart's Reports section) for any sender that is not <vps-public-ip>.
  • tailscale status on the VPS after any reboot. The Homelab series already has a story about a host sitting in "needs login" for thirteen days; a VPS that reboots for a kernel update and loses Tailscale takes the mail server with it.
Final checkpoint
  • DMARC at p=none with reports arriving.
  • MTA-STS policy reachable at its URL from mobile data.
  • A reminder set for two weeks from now to review reports and tighten DMARC.

Glossary for this part

Front door
My name for the rented VPS: the only machine in the design with a public IP, running only HAProxy and Postfix.
PROXY protocol v2
A small binary header HAProxy prepends to a forwarded TCP connection, carrying the original client IP and port. The receiving server must be told which addresses it may trust to send one.
TCP mode
HAProxy forwarding raw bytes without interpreting the protocol. The opposite is HTTP mode, where it reads and rewrites requests.
FCrDNS
Forward-confirmed reverse DNS: the PTR of an IP names a host whose A record is that same IP. Receiving servers check it on every connection.
Open relay
An SMTP server that forwards mail from anyone to anyone. The thing mynetworks and reject_unauth_destination exist to prevent.
Relay route
Stalwart's object for "send this to a specific host instead of looking up the recipient's MX". Here it points at Postfix over Tailscale.
Aggregate report
The daily XML summary a receiver sends to the address in your DMARC record, listing every IP that sent mail as your domain and how it was judged.
