Part 06 · The tools

Roundcube Behind the Tunnel

Webmail is the one piece of this project that is an ordinary website. It runs on the PHP, MariaDB and Caddy I already have on srv1, and it goes out through the Cloudflare Tunnel the same way the portfolio and the LMS do.

Reading time about 12 minutes. The commands here are the plan; part 07 is where they get run in order.

1. What webmail actually is

I had a vague idea that "webmail" was part of the mail server. It is not. Webmail is a mail client, the same category as Thunderbird or the Mail app on a phone. The only difference is where it runs: instead of running on my laptop, it runs on the server and draws its screen in a browser tab.

That means Roundcube talks to Stalwart exactly the way Thunderbird would: it logs in over IMAP to read mail, and over SMTP submission to send it. It stores none of my messages itself. Its own database holds only its own furniture: address book, preferences, session state. If I deleted Roundcube tomorrow, every message would still be in Stalwart, untouched.

Once I understood that, the architecture became obvious. Roundcube is a website that happens to be a mail client. Websites on srv1 have a known pattern. Follow the pattern.

Why this matters for the CGNAT story

Because Roundcube is a browser-facing HTTP app, the Cloudflare Tunnel is exactly the right tool for it, for all the reasons part 01 said the tunnel is the wrong tool for SMTP. Visitors pull a web page; the tunnel carries HTTP; done. The actual mail protocols never leave the VM, because Roundcube and Stalwart are on the same machine and talk over loopback.

2. Why Roundcube, and the clients I didn't pick

Roundcube is a PHP application. It needs a PHP runtime, a database, and a web server to front it. srv1 already has all three, because the LMS needed them: PHP-FPM 8.4 listening on /run/php/php8.4-fpm.sock, MariaDB, and Caddy on port 80 with auto_https off. Nothing new to install at the platform level, which fits the rule I keep coming back to: add the smallest number of new moving parts per feature.

SOGo

SOGo is the webmail Mailcow ships with, and it is a groupware suite: mail, shared calendars, contacts, ActiveSync for phones. It is also heavy, with its own daemon, memcached, and a preference for PostgreSQL or a dedicated MySQL schema. I am one person with one domain. Stalwart already speaks CalDAV and CardDAV natively if I ever want calendars, so SOGo would be solving a problem I don't have, at a RAM cost I'd notice on a 4 GB VM.

SnappyMail (formerly RainLoop)

Perfectly good, lighter than Roundcube, and it doesn't even need a database for basic use. The honest reason I didn't pick it is documentation and reach: Roundcube has been the default self-hosted webmail for nearly twenty years, every hosting guide assumes it, and when something breaks the error message has already been seen by someone else. For a first build that matters more than a smaller footprint.

Stalwart's own /account page

Stalwart's web UI has an end-user area at /account. I want to be accurate about what it is: an account manager, where a user changes their password, manages app passwords, encryption keys and Sieve filters. It is not a full mail client with a reading pane and a compose window. It is useful and I will keep it reachable, but it does not replace webmail.

Road not taken · no webmail at all

Thunderbird on the laptop and the stock mail app on the phone, both pointed at the front door's 993 and 465, would be enough for daily use and remove an entire PHP app from the attack surface. I nearly went this way. The deciding factor was being able to check mail from any browser, including a machine I don't own, without configuring a client. If Roundcube ever becomes a maintenance burden, this is the fallback.

3. The request path, end to end

Two hostnames, two completely different jobs:

HostnamePoints atCloudflare cloudCarries
webmail.22112002.xyzThe tunnel (CNAME, created by cloudflared tunnel route dns)Orange, proxiedHTTPS to Roundcube
mail.22112002.xyzThe VPS public IP (A record)Grey, DNS onlySMTP 25, submission 465, IMAP 993
Never put mail.22112002.xyz in the tunnel

It is tempting because every other hostname went there. If mail.22112002.xyz becomes a proxied Cloudflare record, the MX target resolves to Cloudflare's IPs, which do not answer on port 25, and every inbound message bounces. Part 05 covers why that name has to be a plain, unproxied A record to the front door.

4. Getting Roundcube onto srv1

Debian 13 offers two routes and I want to be honest about the trade.

apt install roundcubeUpstream "complete" tarball
VersionWhatever Debian froze at releaseCurrent stable from roundcube.net
Security updatesAutomatic, via apt upgradeManual: download, unpack, run the update script
Database setupdbconfig asks questions and does itYou create the DB and import the schema yourself
Paths/usr/share/roundcube, /etc/roundcube, /var/lib/roundcubeWherever you unpack it, one folder, obvious
Fits the /var/www/<hostname> patternNeeds a symlink or a Caddy root pointing elsewhereYes, directly

I'm going with the tarball. The apt package is the "forget about it" option and I respect that, but it lags, and the whole point of this project is to understand each piece. Unpacking a tarball into /var/www/webmail.22112002.xyz keeps every site on the box laid out the same way, and the manual database step is the same four SQL lines I already did for the LMS. The price is remembering to update it, which I'm putting on the same checklist as Stalwart upgrades.

# Dependencies Roundcube wants on top of what the LMS already pulled in
sudo apt install -y php8.4-intl php8.4-mbstring php8.4-xml php8.4-zip php8.4-gd php8.4-curl php8.4-mysql

# Fetch and unpack (check roundcube.net/download for the current version number)
cd /tmp
curl -LO https://github.com/roundcube/roundcubemail/releases/download/<version>/roundcubemail-<version>-complete.tar.gz
tar xzf roundcubemail-<version>-complete.tar.gz
sudo mv roundcubemail-<version> /var/www/webmail.22112002.xyz
sudo chown -R www-data:www-data /var/www/webmail.22112002.xyz/temp /var/www/webmail.22112002.xyz/logs
Verify at build time

Recent Roundcube releases ship a public_html/ directory meant to be the web root, so that config/, temp/ and logs/ sit outside anything the web server can serve. Older releases put index.php at the top level. After unpacking, run ls /var/www/webmail.22112002.xyz and set the Caddy root to whichever directory actually holds index.php. The exact PHP extension list is also version dependent; the installer page lists what is missing.

5. The database

Same recipe as the LMS, and the same two lessons apply: a database user is credentials plus a grant, and 'localhost' means the Unix socket, not 127.0.0.1.

sudo mariadb
CREATE DATABASE roundcubemail CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'roundcube'@'localhost' IDENTIFIED BY 'a_real_password';
GRANT ALL PRIVILEGES ON roundcubemail.* TO 'roundcube'@'localhost';
FLUSH PRIVILEGES;
# Import the schema that ships in the tarball
sudo mariadb roundcubemail < /var/www/webmail.22112002.xyz/SQL/mysql.initial.sql

Roundcube's connection string then uses the socket form so it lines up with the @'localhost' user:

$config['db_dsnw'] = 'mysql://roundcube:a_real_password@localhost/roundcubemail';

6. Pointing Roundcube at Stalwart

This is the part that is specific to this build, and it has one trap. The file is config/config.inc.php, created by copying config/config.inc.php.sample.

<?php
$config['db_dsnw'] = 'mysql://roundcube:a_real_password@localhost/roundcubemail';

// Stalwart, on the same machine, over loopback
$config['imap_host'] = 'tls://127.0.0.1:143';   // STARTTLS on 143; or 'ssl://127.0.0.1:993'
$config['smtp_host'] = 'tls://127.0.0.1:587';   // submission with STARTTLS
$config['smtp_user'] = '%u';                    // reuse the IMAP login for sending
$config['smtp_pass'] = '%p';

// The certificate Stalwart presents is for mail.22112002.xyz, not 127.0.0.1.
// Tell PHP which name to check it against, or TLS verification fails.
$config['imap_conn_options'] = [
  'ssl' => ['verify_peer' => true, 'verify_peer_name' => true, 'peer_name' => 'mail.22112002.xyz'],
];
$config['smtp_conn_options'] = [
  'ssl' => ['verify_peer' => true, 'verify_peer_name' => true, 'peer_name' => 'mail.22112002.xyz'],
];

$config['des_key'] = 'exactly-24-random-chars!';   // generate: openssl rand -base64 18
$config['product_name'] = 'Mail · 22112002.xyz';
$config['plugins'] = ['archive', 'zipdownload', 'managesieve'];
$config['enable_installer'] = false;

The trap: which name is the certificate for?

Stalwart's certificate, obtained in part 07 through ACME with a DNS challenge, is for mail.22112002.xyz. Roundcube connects to 127.0.0.1. PHP's TLS layer compares the name it connected to against the name in the certificate, sees that 127.0.0.1 is not mail.22112002.xyz, and refuses. There are two honest fixes and one dishonest one.

  • Set peer_name in the connection options, as above. Connect to the IP, verify against the real name. This is the one I'm using.
  • Connect to the name, but override where it resolves. Add 127.0.0.1 mail.22112002.xyz to /etc/hosts on srv1, then set imap_host to tls://mail.22112002.xyz:143. Equivalent, slightly more magic, but it also makes openssl s_client -connect mail.22112002.xyz:993 on the box test the local server, which is handy.
  • Turn verification off with verify_peer => false. It would work. It is also the kind of shortcut that quietly stays forever. Not doing it.

Why not simply let mail.22112002.xyz resolve normally? Because in public DNS that name points at the VPS. From srv1, a connection to it would go out of the house, across the internet to the front door, through HAProxy, back down Tailscale, and into the very same Stalwart process sitting on the same VM. It would work. It would also be absurd, and it would break the moment the VPS was down even though both halves of webmail were fine. Loopback is the right wire.

7. Caddy and the tunnel

A new block in /etc/caddy/Caddyfile, following the house style with the explicit :80:

webmail.22112002.xyz:80 {
	root * /var/www/webmail.22112002.xyz/public_html
	encode gzip

	# Belt and braces: never serve these even if the root is wrong
	@private path /config/* /temp/* /logs/* /SQL/* /bin/* /installer/*
	respond @private 403

	php_fastcgi unix//run/php/php8.4-fpm.sock
	file_server
}
sudo caddy validate --config /etc/caddy/Caddyfile
sudo systemctl reload caddy

Then the DNS record and the ingress rule, the exact two steps every site on this box has needed:

cloudflared tunnel route dns homelab webmail.22112002.xyz
# /etc/cloudflared/config.yml, above the http_status:404 catch-all
  - hostname: webmail.22112002.xyz
    service: http://127.0.0.1:80
sudo systemctl restart cloudflared

Notice what is not here: no mail.22112002.xyz, no 25, no 465, no 993. Caddy and the tunnel know nothing about mail. They know about one more PHP website.

8. Hygiene, learned the hard way on the LMS

  • Delete installer/ after setup. Roundcube's web installer can read and rewrite its own config. It must not exist on a public hostname once you're done. sudo rm -rf /var/www/webmail.22112002.xyz/installer, and enable_installer = false as a second lock.
  • Turn on catch_workers_output = yes in /etc/php/8.4/fpm/pool.d/www.conf. Without it PHP errors from workers vanish and a blank page is all you get. This was the second real bug in the LMS build and I'm not debugging it twice.
  • Roundcube's own log is logs/errors.log inside the install (or syslog if configured). For login problems, it is more useful than Caddy's log, because it records what the IMAP server said.
  • Put the DB password in the same place as the LMS's, in a password manager, not only in config.inc.php.

Glossary for this part

Webmail
A mail client that runs on a server and renders in a browser. It reads and sends through IMAP and SMTP like any other client, and stores no messages itself.
Roundcube
The long-standing open source PHP webmail. Needs PHP, a database and a web server.
SOGo
A heavier groupware suite with webmail, calendars and contacts; what Mailcow bundles.
SnappyMail
A lighter PHP webmail descended from RainLoop; a fine alternative with less documentation around it.
Submission (port 587 / 465)
The SMTP port a client uses to hand its own outgoing mail to its own server, with a login. Different from port 25, which is server-to-server.
STARTTLS vs implicit TLS
STARTTLS begins in plain text and upgrades to encryption on request (ports 143, 587). Implicit TLS encrypts from the first byte (ports 993, 465). Roundcube's tls:// prefix means STARTTLS; ssl:// means implicit.
peer_name
The hostname PHP checks a TLS certificate against. Needed when you connect by IP but the certificate is for a name.
Loopback
127.0.0.1: the machine talking to itself. Traffic on it never leaves the VM and is unaffected by CGNAT or anything in Cloudflare.
