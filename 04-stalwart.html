Part 04 · The tools

Stalwart, and the Stacks I Didn't Pick

Every mail server tutorial I had ever skimmed was a tour of five separate programs stitched together with config files in five different dialects. Stalwart is one program. This part is about what that one program does, how it is configured, and why the obvious alternatives lost on a 4 GB VM that already has a job.

Facts checked against the Stalwart documentation at release v0.16.25 (5 October 2026). Anything I could not verify is marked.

1. What a mail server traditionally is

Part 02 described the life of a message: submitted, queued, handed to another server, filtered, stored, read back over IMAP. Historically each of those jobs was a separate piece of software, written by separate people, each with its own configuration language:

JobClassic toolConfig lives in
Accept and send SMTP, run the queuePostfixmain.cf, master.cf, assorted lookup tables
Store mailboxes, serve IMAP, authenticate usersDovecotdovecot.conf plus a conf.d/ directory
Spam filteringRspamd (or SpamAssassin)UCL files under /etc/rspamd/local.d/
DKIM signingOpenDKIM, or Rspamd's moduleIts own key tables and a milter socket
Virus scanningClamAVIts own daemon and signature updates
TLS certificatescertbotA renewal timer and hooks to restart two daemons
User and domain listMySQL/MariaDB or flat filesSchema that Postfix and Dovecot both query
WebmailRoundcubePHP config, its own database

None of these tools are bad. Postfix in particular is one of the most carefully engineered pieces of software on the internet. The problem is the seams. Postfix hands to Dovecot over LMTP. Rspamd hooks into Postfix as a milter. OpenDKIM is another milter. Dovecot authenticates Postfix's submission users over a socket. Each seam is a place where two configs have to agree about a path, a port, a socket, a user name, and each one fails silently when they do not. The Homelab series already has a story about a PHP socket version mismatch that produced no error at all. A classic mail stack has about six of those seams.

2. What Stalwart is

Stalwart is a mail and collaboration server written in Rust, released as a single binary. One process speaks SMTP (receiving, submission and outbound delivery), IMAP4, POP3, JMAP (the modern JSON replacement for IMAP), ManageSieve (server-side filter rules), and CalDAV, CardDAV and WebDAV for calendars, contacts and files. It is dual-licensed: AGPL-3.0 for everyone, plus a paid enterprise licence for features I do not need.

It stores everything in a database backend of your choice: RocksDB (embedded, single node, what I use), FoundationDB, PostgreSQL, MySQL, SQLite, or an S3-compatible bucket for message bodies. For one VM with one disk, RocksDB means no extra service to run.

The resource numbers are what made it fit this project. The documentation states roughly 100 MB of RAM idle, that 1 GB is "generally sufficient" for 5 to 10 users, and that a single CPU core is enough for around 5 users. srv1 has 4 GB shared with Caddy, PHP-FPM, MariaDB and the tunnel. A mail server that wants a quarter of that is fine. One that recommends 6 GB on its own is not.

3. How it is configured, and why that surprised me

I expected a big TOML file. Older Stalwart versions had one, and most blog posts still show it. The current model is different, and it is worth understanding before touching anything, because "where is the config?" has a two-part answer.

Part one: a tiny file. /etc/stalwart/config.json holds only one thing, the location of the data store:

{"@type":"RocksDb","path":"/var/lib/stalwart/"}

Part two: the database. On start, Stalwart reads that file, opens the store, and loads everything else from it: domains, accounts, listeners, TLS certificates, spam rules, routes, rate limits. Each of those is a typed object (a Domain, a NetworkListener, an MtaRoute, and so on). You edit them through the WebUI at /admin, or through stalwart-cli, both of which talk to the server's JMAP management API. Some settings are compiled into the running core and only apply after a ReloadSettings action; the WebUI tells you when that is needed.

Honest tradeoff

I like being able to grep a config directory, and with Stalwart I mostly cannot. The upside is that the WebUI validates each object as you save it, so the class of mistake where a typo in a file takes a service down on reload is mostly gone. Caddy's caddy validate taught me how much that is worth. The downside is that the mental model from every Postfix tutorial does not transfer.

4. First start: bootstrap mode

Installation is one script. It downloads the binary to /usr/local/bin/stalwart, creates /var/lib/stalwart/ for data and /var/log/stalwart/ for logs, and installs a systemd unit:

curl --proto '=https' --tlsv1.2 -sSf https://get.stalw.art/install.sh -o install.sh
sudo sh install.sh

Because there is no config.json yet, the first start enters bootstrap mode. No mail services run. The server listens on plain HTTP port 8080 (changeable with STALWART_RECOVERY_MODE_PORT) and serves only the WebUI and management API. It generates a temporary administrator account and prints the password once to standard output. On systemd that means:

sudo journalctl -u stalwart -n 200 | grep -A8 'bootstrap mode'

If you would rather not fish a password out of a log, pin one beforehand with the environment variable STALWART_RECOVERY_ADMIN=admin:<password> in the unit's environment.

Then open http://<host>:8080/admin, log in, and the setup wizard asks for the server hostname, the default domain, the storage backend settings and the user directory. When it finishes, Stalwart writes config.json, creates a permanent admin account, restarts into normal operation, moves the WebUI to https://<hostname>/admin, and disables administration on port 8080. The temporary account stops working.

Needs GitHub reachable

The WebUI is not baked into the binary. On first start Stalwart downloads the UI bundle from GitHub over HTTPS. If srv1 cannot reach GitHub, /admin and /account return 404 and nothing in the logs says "install the UI". The Homelab series has a DNS story that would have produced exactly this symptom.

5. The five features that made it fit a CGNAT homelab

Any mail server can receive and store mail. These five are the ones that line up with the specific constraints from parts 01 and 03: no public ports at home, every inbound connection arriving from one relay, and outbound mail that has to leave from somewhere else.

5.1 Certificates with no open ports: ACME over DNS-01

Caddy gets certificates automatically because it can answer on port 80 or 443. At home I have neither open to the internet, and I am not going to. Stalwart supports four ACME challenge types, configured as AcmeProvider objects under Settings › TLS › ACME Providers:

ChallengeNeeds a public port?Works for me?
HTTP-0180No
TLS-ALPN-01443No
DNS-01None. Publishes a _acme-challenge TXT record, waits for propagation, removes it.Yes
DNS-PERSIST-01None. One long-lived TXT record authorises the ACME account for the domain.Yes, newer

DNS-01 requires that the domain has automatic DNS management turned on, which is the next feature. Then a Domain with certificateManagement set to Automatic gets its certificate requested and renewed by a scheduled task with no port ever opened at home.

5.2 Automatic DNS: Stalwart writes its own records

Part 03 lists about ten DNS records a mail domain needs, and the DKIM one is a long public key that gets rotated. Stalwart can publish and maintain all of them itself. You create a DnsServer object under Settings › Network › DNS › DNS Providers with credentials for your DNS host, then set the domain's dnsManagement to Automatic and point it at that provider. Cloudflare is supported, along with Route 53, Google Cloud DNS, OVH, deSEC, DigitalOcean, Bunny, Porkbun, DNSimple, Spaceship, and any RFC 2136 server. The default publishRecords list covers DKIM, SPF, MX, DMARC, SRV, MTA-STS, TLS-RPT, CAA, autoconfig and autodiscover. The server polls afterwards to confirm the records are visible.

For 22112002.xyz on Cloudflare this means one scoped API token and no copy-pasting of DKIM keys into the dashboard. The one record it does not manage is the plain A record for mail.22112002.xyz, which has to point at the VPS and stay DNS-only (grey cloud). That one I set by hand.

5.3 The spam filter is built in

No Rspamd to bolt on. The filter does DNSBL lookups, greylisting, SPF/DKIM/DMARC evaluation, a statistical classifier that learns from what you mark as spam, phishing checks, and optionally an LLM-based classifier if you point it at a model API. For this build the important part is that it sits inside the same process that receives the connection, which matters for the next feature.

5.4 PROXY protocol: seeing the real sender through the relay

In part 05's design every inbound connection reaches srv1 from the VPS over Tailscale. Without help, Stalwart would see every sender as the VPS's Tailscale address, and every IP-based check would be useless: DNSBL would look up the wrong address, SPF would evaluate the wrong address, rate limiting and auto-ban would punish the VPS. HAProxy solves this with the PROXY protocol: a small header at the start of the TCP stream that says "the real client was 209.85.x.x, port such-and-such, and here is whether it used TLS". Stalwart accepts versions 1 and 2, including the version-2 TLV extensions, but only from addresses listed as trusted. That list is proxyTrustedNetworks on the system settings (Settings › Network › General) or, per listener, overrideProxyTrustedNetworks on the NetworkListener, which replaces the global list for that listener. A listener decodes either PROXY headers or X-Forwarded-For, never both on one connection.

5.5 Outbound through a relay: the MtaRoute

Outbound mail must leave from the VPS's IP, not from my house. Stalwart's outbound side is strategy-driven: for each recipient it evaluates an MtaOutboundStrategy that picks a queue, a retry schedule and a route. A route of variant Relay (Settings › MTA › Outbound › Routes) has an address, a port (default 25), a protocol of smtp or lmtp, implicitTls, allowInvalidCerts, and optional authUsername and authSecret. Point it at the VPS over Tailscale and every message for a remote domain gets handed there instead of looked up by MX.

Verify during the build

The documentation says the relay route is "selected via route expressions in MtaOutboundStrategy" for the recipients you choose. I have the object names but not the exact expression syntax for "every recipient that is not a local domain". Part 08 will record what the WebUI actually offered.

6. The stacks I didn't pick

Road not taken · Postfix + Dovecot + Rspamd

For it: the most documented stack on earth, the most CV-relevant, decades of hardening, and every error message has a forum thread. If a future job says "mail", it says Postfix. Against it, here: five daemons and five config dialects on a 4 GB VM that is also a web server, with milter sockets and LMTP paths as the seams in figure 1. I have already lost an afternoon to one silent socket mismatch in this homelab. The nginx decision in the Homelab series was the same trade: fewer places to make a syntax mistake beat the more expected tool. I may still build this stack on a throwaway VM later just to have done it.

Road not taken · Mailcow

For it: a genuinely excellent all-in-one, with SOGo webmail and calendar, a polished admin UI, and a huge community. Against it: it is a dozen Docker containers and its own documentation recommends 6 GB of RAM or more. On a VM with 4 GB total, half already spoken for, that is not a tight fit, it is a non-fit. It would need its own VM, and then I am back to planning a second VM for mail instead of using the spare capacity I have.

Road not taken · docker-mailserver

For it: the sensible middle ground. Postfix, Dovecot and Rspamd pre-wired inside one container, around 600 MB of RAM, configuration in plain files you can version. It would run on srv1. Against it: it is still the five-daemon mental model, just with the seams pre-glued by someone else, and there is no admin UI, so account management is a shell script. It also brings Docker onto a VM that so far runs everything as plain systemd services, which the Homelab series deliberately avoided until an app needed it.

Road not taken · Maddy

For it: a single Go binary with the same "one process" idea, very light, a clean config file. Against it: a much smaller ecosystem, no JMAP, no built-in web admin, and less momentum. If Stalwart had not existed I would have looked hard at it.

And Stalwart's own honest column: it is younger than any of the above, there are fewer blog posts about it, its configuration moved from a file into a database so my muscle memory is useless, and the WebUI needs GitHub reachable on first start. I am accepting all of that for one process, one log, one service to restart, DNS-01 certificates, and a PROXY-aware spam filter that fits the architecture I was forced into in part 01.

Glossary for this part

Milter
"Mail filter": the plugin protocol Postfix and Sendmail use to call out to external programs such as Rspamd or OpenDKIM during an SMTP session. One of the seams.
LMTP
Local Mail Transfer Protocol, a cut-down SMTP used to hand a message from the MTA to the program that stores it. Another seam in the classic stack.
JMAP
JSON Meta Application Protocol, the IETF's modern replacement for IMAP. Stateless, HTTP-based, and what Stalwart's own account UI uses.
RocksDB
An embedded key-value database that lives in a directory, no separate server. Stalwart's single-node default.
Bootstrap mode
Stalwart's first-start state: no config.json, WebUI only on port 8080, one-time admin password printed to the log.
ACME DNS-01
Proving domain control to a certificate authority by publishing a TXT record instead of answering on port 80 or 443. The only ACME method that works with no public ports.
PROXY protocol
HAProxy's header at the start of a forwarded TCP connection that carries the original client's IP and TLS status, so the backend can act as if the client had connected directly.
MtaRoute
Stalwart's object describing where outbound mail goes: by MX lookup, to a relay, or to local delivery.
