Part 01 · The problem

Why a Cloudflare Tunnel Can't Carry Mail

I started this project with one sentence in my head: "the websites go through the tunnel, so the mail server can too." That sentence is wrong, and understanding exactly why it is wrong decided the whole architecture.

Reading time about 10 minutes. No commands in this part, only ideas.

1. The assumption I walked in with

By the time I wanted email, the homelab had a comfortable pattern. Anything I wanted the public to reach followed the same four steps: a folder under /var/www, a block in the Caddyfile, a hostname in the tunnel's ingress list, one cloudflared tunnel route dns command. CGNAT had stopped being a problem months ago, because the tunnel dials out and Cloudflare relays visitors in down that already-open connection.

So the plan wrote itself: install a mail server on srv1, add mail.22112002.xyz to the tunnel, done. I had even picked the software before I checked whether the plan could work.

It cannot. Not "it is hard", not "it needs a paid plan". The tunnel is the wrong shape for the protocol, and no amount of configuration changes a shape.

2. Pulled protocols and pushed protocols

The thing I had never thought about is who starts the conversation.

When somebody visits 22112002.xyz, their browser starts it. It opens a connection to whatever IP the DNS name points at, says "GET / please", and waits. The server only ever answers. Every website on the internet works this way, which is why a tunnel can publish a website at all: Cloudflare's edge is the thing the browser connects to, and Cloudflare already has a line open to my VM to pass the request down. The browser never needs to reach my house. It needs to reach Cloudflare, and Cloudflare is very reachable.

Email is the opposite. When Gmail has a message for me@22112002.xyz, Gmail starts the conversation. Its server looks up which machine handles mail for my domain, opens a TCP connection to that machine on port 25, and starts talking SMTP. Nobody asked it to; it decided to, because it had a message to deliver. The receiving side has to be a machine with a real, routable address that accepts an inbound connection on port 25 from any server in the world, at any time.

That is exactly the thing CGNAT takes away. Not "a port" in general, but the ability for the outside world to initiate. The Homelab series worked around that for the web because the web does not need my house to accept anything: Cloudflare accepts, and my VM collects. Mail does not have a Cloudflare in the middle. The sender wants my MX host, directly, on 25.

3. What Cloudflare Tunnel actually is

I had been treating the tunnel as "a pipe from the internet to my VM". It is narrower than that. A tunnel's public hostnames accept HTTP and HTTPS. Cloudflare's edge terminates the visitor's TLS, reads the HTTP request, and forwards that request down the tunnel. It is an HTTP reverse proxy with a very long cable. The ingress rules in config.yml even say so: every service line is http://localhost:something.

Cloudflare does have ways to carry other TCP protocols, and I checked each one:

  • Arbitrary TCP through a tunnel exists, but only for clients that run Cloudflare's own software (cloudflared access or the WARP client) to reach it. That is for me SSHing into a box. Gmail's mail server is not going to install WARP to talk to mine.
  • Cloudflare Spectrum is the product that proxies raw TCP for the public, including SMTP. It is on the Enterprise plan. Not a homelab price.
  • Cloudflare Email Routing is free and does receive mail for your domain on Cloudflare's own servers. But it only forwards to an existing mailbox elsewhere, such as Gmail. There is no inbox, no IMAP, nothing I would call "my mail server". It solves a different problem.

The honest summary: the tunnel is an HTTP tool, and mail is not HTTP.

4. The other tunnels I looked at, and why they fail too

Once I understood the shape of the problem, I went looking for any service that would accept port 25 for me and hand the connection down to my house. The list is short and every entry has the same flaw.

The difference is that for private access Tailscale gives me that rendezvous for free, and for SMTP nobody does.

5. Receiving is only half of it: sending is worse

Suppose I ignored all of the above and only wanted to send mail from home. Outbound connections work fine under CGNAT, so the TCP part would succeed. The mail would still fail, for reasons that have nothing to do with my network and everything to do with how the receiving world judges a sender.

  1. The IP has no reverse DNS I control. Receiving servers look up the PTR record for the connecting IP and expect it to name a mail host that resolves back to that same IP. My ISP's shared address has whatever PTR the ISP gave it, if any. I cannot change it.
  2. Residential ranges are listed as "should not send mail". The Spamhaus Policy Block List catalogues IP ranges that ISPs have declared are for end users, not mail servers. Most big receivers consult it. A connection from such a range is refused or junked regardless of content.
  3. The IP is shared with strangers. Under CGNAT many households share my outbound address. If one of them has an infected laptop sending spam, the address's reputation is theirs, not mine.
  4. SPF cannot name my address because it changes, and because it is not mine to name.

So the machine with the public IP is not only needed to receive. Outbound mail has to leave from it too, so that the IP Gmail sees has a PTR record I set, is not on a residential list, and carries only my reputation. Part 03 goes through each of those checks properly.

6. The decision this forced

Three honest options came out of this, and I wrote them down before picking:

Road not taken · no real mail server

Cloudflare Email Routing forwards inbound to Gmail; a transactional relay like Brevo or Resend sends outbound for my apps. Costs nothing, runs nowhere. But there is no mailbox, no IMAP, no Roundcube, and nothing to learn. I would be renting the interesting part.

Road not taken · put the whole mail server on a VPS

Rent a VPS, install everything there, read it from home. Fewest moving parts and the easiest deliverability. But then the mailboxes, the one piece of data I actually care about, live off-site on the cheapest box I could find, and srv1 and its spare RAM sit idle. It also stops being a homelab project.

Chosen · a thin front door, with the mail server at home

Rent the smallest VPS that allows port 25 and lets me set PTR. Run nothing on it but a TCP forwarder for inbound and a minimal relay for outbound, both talking to srv1 over Tailscale. The mail server, the mailboxes, the spam filter and the webmail all stay on srv1. The VPS owns the public IP and the reputation; my house owns the data.

It is the first part of the homelab that costs money, roughly the price of a coffee a month, and I am treating that the same way I treated Tailscale's coordination server: a public rendezvous point is a thing that structurally cannot be self-hosted from behind CGNAT, so renting exactly that and nothing more is the honest minimum.

Postscript, evening of 8 October 2026

The VPS was never rented. The same afternoon it turned out the budget for it was zero, and a second round of investigation found a front door that costs nothing: Cloudflare Email Routing receives for the domain, a small Worker opens a TCP connection back through my own tunnel and hands each message to Stalwart, and a free relay sends outbound from a reputable IP. The constraint in this part still holds, something with a public IP must accept port 25, it just turned out that something could be rented for free in exchange for different trade-offs. The rewritten part 05 has the design and part 08 the build.

Glossary for this part

Pulled vs pushed protocol
My shorthand for who opens the connection. The web is pulled: the visitor connects to the server. Mail delivery is pushed: the sending server connects to the receiving one.
Port 25
The TCP port every mail server in the world uses to hand messages to another mail server. If nobody answers there, the domain cannot receive mail.
MX record
The DNS record that names which host accepts mail for a domain. It must point at a hostname with an A or AAAA record, never at a Cloudflare proxied address.
PTR record
Reverse DNS: the name an IP address claims to have. Only whoever controls the IP block can set it, which is why it has to be the VPS provider's IP and not my ISP's.
Spamhaus PBL
A public list of IP ranges whose owners have said "end-user devices live here, do not accept mail directly from them". Residential and mobile ranges are on it by design.
Cloudflare Spectrum
Cloudflare's raw-TCP proxy product. It would solve this problem and is priced for enterprises.
