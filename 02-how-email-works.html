Part 02 · The theory

How Email Actually Works

I have sent email every day for most of my life and, until this project, could not have told you what happens between pressing Send and the message appearing somewhere else. This part follows one message the whole way, because every configuration decision later is a decision about one of these steps.

Reading time about 15 minutes. Still no commands, but there is a real SMTP transcript to read.

1. Four jobs, not one program

The first thing that confused me is that "a mail server" is not one thing. The protocols were designed in the early 1980s by people who assumed each job might run on a different machine, so the specifications name four roles. Modern software bundles them, but the names still show up in every log line and error message, so they are worth learning once.

RoleStands forWhat it doesIn my build
MUAMail User AgentThe program a person uses. Composes, displays, files messages.Thunderbird, the phone's mail app, Roundcube
MSAMail Submission AgentAccepts a new message from an authenticated user and hands it to the MTA. Checks the user is allowed to send as that address.Stalwart, on ports 465 and 587
MTAMail Transfer AgentMoves messages between servers. Looks up where the recipient's domain lives, connects there on port 25, and keeps retrying if it cannot.Stalwart at home, plus the Postfix relay on the VPS for the last hop out
MDAMail Delivery AgentTakes a message that has arrived for a local user and files it into their mailbox. This is where filters (Sieve) run.Stalwart

The reason I care about the split is that the MSA and the MTA treat connections completely differently, even when they are the same program. An MSA talks to my users: it demands a password, it is reached on 465 or 587, and it is allowed to send mail from my domain. An MTA talks to strangers: it accepts mail on port 25 from any server in the world, without a password, but only mail to my domain. A server that accepts mail from strangers to anywhere is an "open relay", which is the single fastest way to get a new IP blacklisted. Keeping these two doors separate is the first principle of the whole setup.

2. The journey of one message

Say I am in Roundcube on webmail.22112002.xyz and I write to a friend at Gmail. Here is everything that happens, in order.

  1. Submission. Roundcube (the MUA) connects to Stalwart (acting as MSA), authenticates as me, and hands over the message. Stalwart checks the From: address belongs to my account, stamps the message with a DKIM signature (Part 03), and puts it in its outbound queue.
  2. Lookup. Stalwart (now the MTA) asks DNS: who receives mail for gmail.com? The answer is a list of MX records, each a hostname with a priority number. It picks the lowest number first and resolves that hostname to an IP.
  3. Transfer. It opens a TCP connection to that IP on port 25 and has the SMTP conversation in the next section. In my build this step is split: Stalwart hands the message over Tailscale to the relay on the VPS, and the relay does the port-25 connection to Gmail, so the IP Gmail sees is the VPS's. Part 05 covers why.
  4. Acceptance or deferral. Gmail's MTA either says "250, queued" and the message is now its responsibility, or it refuses. If it refuses with a temporary code, my side keeps the message and tries again later. If it refuses permanently, my side generates a bounce back to me.
  5. Delivery. Inside Google, an MDA runs its spam checks and files the message into my friend's mailbox.
  6. Retrieval. My friend's phone connects over IMAP (or Google's own API) and pulls the message down to display it.

3. Submission: 587 and 465, and why there are two

Historically everything, including clients sending new mail, went through port 25. Spam made that untenable, because an ISP could not tell a customer's laptop sending one message from a compromised laptop sending ten thousand. So a separate submission port was defined, where authentication is mandatory, and ISPs started blocking outbound 25 from residential connections entirely. That is why your phone's mail settings never say 25.

  • Port 587 with STARTTLS. The connection begins in plain text, the client says EHLO, the server advertises STARTTLS, and they upgrade to encryption before any password is sent. This was the standard for years. Its weakness is that an attacker in the middle can strip the STARTTLS advertisement and the client might carry on in the clear.
  • Port 465 with implicit TLS. The connection is TLS from the first byte, exactly like HTTPS. There is nothing to strip. This port was briefly deprecated and then brought back as the recommended one, so older guides argue about it. I am treating 465 as primary and offering 587 as well for clients that insist.

Both are MSA doors: no password, no entry. Stalwart runs one listener per port and the only difference in config is a single "implicit TLS" switch.

4. The lookup: MX records and priorities

Before an MTA can connect anywhere it needs to turn gmail.com into an IP that accepts mail. It does not use the domain's A record for that. It asks for MX records, which exist precisely so that the web server and the mail server for a domain can be different machines.

$ dig +short MX gmail.com
5 gmail-smtp-in.l.google.com.
10 alt1.gmail-smtp-in.l.google.com.
20 alt2.gmail-smtp-in.l.google.com.
30 alt3.gmail-smtp-in.l.google.com.
40 alt4.gmail-smtp-in.l.google.com.

Each line is a priority and a hostname. Lower number wins; the others are fallbacks tried in order if the first does not answer. Each hostname then has an ordinary A or AAAA record giving the IP. For my domain there will be exactly one line, 10 mail.22112002.xyz., and mail.22112002.xyz will have an A record pointing at the VPS.

Two rules I learned the hard way while reading about this:

  • If a domain has no MX record at all, senders fall back to its A record and try port 25 there. That is a trap for a domain whose A record is Cloudflare's proxy: mail silently goes to an IP that does not speak SMTP. Always publish an MX.
  • The MX target must be a hostname, not an IP, and that hostname must not be a CNAME. Part 03 adds the Cloudflare-specific rule: the target's A record must be grey-cloud, DNS only.

5. The SMTP conversation, line by line

SMTP is a text protocol. You can type it by hand, and in Part 09 I do, because it is the fastest way to see exactly where a delivery fails. Here is a complete, slightly trimmed transaction from a client to a server. Lines starting with C: are sent by the connecting side, S: by the receiving side.

S: 220 mail.22112002.xyz ESMTP Stalwart              ← greeting; 220 means "ready"
C: EHLO sender.example.org                            ← "hello, this is who I claim to be"
S: 250-mail.22112002.xyz
S: 250-STARTTLS                                       ← the server lists what it supports
S: 250-SIZE 52428800
S: 250 PIPELINING
C: STARTTLS
S: 220 Go ahead                                       ← from here on the channel is encrypted
C: EHLO sender.example.org                            ← must say hello again after TLS
S: 250 ...
C: MAIL FROM:<alice@example.org>                       ← the ENVELOPE sender (return path)
S: 250 OK
C: RCPT TO:<me@22112002.xyz>                           ← the ENVELOPE recipient
S: 250 OK                                             ← "I accept mail for that address"
C: DATA
S: 354 Start mail input; end with <CRLF>.<CRLF>
C: From: Alice <alice@example.org>                    ← the HEADERS begin; this From: is just text
C: To: me@22112002.xyz
C: Subject: hello
C: Date: Wed, 08 Oct 2026 10:12:00 +0200
C:
C: Hi, testing.
C: .                                                  ← a line with only a dot ends the message
S: 250 2.0.0 Message queued as 1a2b3c                 ← the server now owns the message
C: QUIT
S: 221 Bye

Three things in there changed how I think about mail.

The reply codes are the protocol. Every server line starts with three digits and the first digit is the only thing that matters to a machine:

First digitMeaningWhat the sender does
2xxSuccessMoves on to the next step. 250 after DATA is the moment responsibility transfers.
3xxKeep going, I need moreOnly 354 in practice: "send me the message body now".
4xxTemporary failureKeeps the message in its queue and retries later, typically for up to a few days, with growing gaps. Greylisting (Part 04) deliberately answers 450 to first-time senders because real MTAs retry and most spam bots do not.
5xxPermanent failureGives up and sends a bounce to the envelope sender. 550 user unknown and 554 rejected due to policy are the ones I will meet.

The envelope and the headers are different things. The address in MAIL FROM is the envelope: it is what the receiving server uses to send a bounce, and it is what SPF checks. The From: line inside DATA is a header: it is what the human sees in their mail client, and it is what DMARC checks. They are usually the same for a person writing a message, but they are routinely different for mailing lists, forwarders and newsletters, and the whole trick of email forgery is that nothing in SMTP itself stops me typing any From: I like. Part 03 is about the DNS records that were bolted on later to close that gap.

Nothing is authenticated on port 25. There was no password anywhere in that transcript. The receiving server accepted a message from a stranger purely because RCPT TO named a mailbox it hosts. That is correct behaviour for an MTA, and it is why everything that makes mail trustworthy lives in DNS rather than in SMTP.

6. The queue: why email is slow on purpose

Because a 4xx reply means "try later", every MTA has a queue: a folder of messages it has accepted but not yet delivered, with a next-attempt time on each. If Gmail is briefly unreachable, or greylists me, or my VPS is rebooting, nothing is lost; the message waits and goes out on the next attempt. The retry gaps grow (a few minutes, then half an hour, then hours) and after a configurable deadline, usually a few days, the MTA gives up and bounces.

In my build there are two queues on the outbound path: Stalwart's at home and Postfix's on the VPS. That is fine, and it is actually useful. If the Tailscale link is down, Stalwart holds the mail. If Gmail is down, Postfix holds it. Each queue is visible (Stalwart in its web admin, Postfix with mailq), and Part 09 uses them as evidence of where a delivery is stuck.

The mental model

Email is store-and-forward, not a phone call. "Sent" means "my server accepted it", not "it arrived". Nothing between my Send button and their inbox is required to be online at the same moment, which is what made the protocol survive forty years of flaky networks, and what makes debugging it a matter of finding which queue the message is sitting in.

7. Delivery and storage

Once my MTA has said 250 queued for an inbound message, the MDA takes over. It runs the spam filter, applies the user's Sieve rules (for example "anything from the LMS goes to a folder"), and writes the message into a mailbox. Traditionally that mailbox was a directory of files on disk, one message per file, in a layout called Maildir. Stalwart does not use Maildir. It keeps messages in its own database (RocksDB in my case), with the message body stored as a blob and the metadata (flags, folders, threads, full-text index) in indexed tables. The practical consequence is that there is no folder of .eml files to poke at, and backup means backing up /var/lib/stalwart rather than a mail directory. Part 04 goes into this.

8. Reading it back: IMAP, JMAP and POP3

Delivery puts a message in a mailbox on the server. A separate protocol gets it from there to a screen.

IMAP (ports 143 with STARTTLS, 993 implicit TLS) is the one every mail client speaks. The mailbox stays on the server; the client synchronises a view of it, so the same folders and read/unread flags appear on the laptop and the phone. It is a chatty protocol designed in the dial-up era, with many round trips per action, which is why mail apps on a slow connection feel sluggish, and why the whole-inbox-resync problem exists.

JMAP is the modern replacement: the same mailbox-on-the-server idea, but as a JSON API over HTTPS, batching many operations into one request and pushing changes to the client. Few desktop clients speak it yet, but Stalwart implements it natively and it is the protocol its own account web UI uses. For me this is one of the arguments for Stalwart over the traditional stack: I get the old protocol for Thunderbird and the new one for free.

POP3 (110/995) downloads messages and, by default, deletes them from the server. It is what people used before always-on connections; I am leaving it switched off.

Glossary for this part

MUA / MSA / MTA / MDA
The four roles: the user's client, the door that accepts new mail from authenticated users, the engine that moves mail between servers, and the piece that files arriving mail into mailboxes.
Submission
A client handing a new message to its own server, on 465 or 587, with a password. Distinct from transfer on port 25, which has no password.
Open relay
A server that forwards mail from strangers to anywhere. Spammers hunt for them; getting listed as one ends a new IP's usefulness in hours.
MX record
DNS record naming the host(s) that accept mail for a domain, each with a priority. Lower is tried first.
Envelope vs header
The envelope is MAIL FROM / RCPT TO, used for routing and bounces. The headers are the From: / To: lines inside the message, shown to humans. They can differ, and forgery lives in that gap.
Reply code
The three digits that start every SMTP server response. 2 = success, 3 = send more, 4 = temporary failure (retry), 5 = permanent failure (bounce).
Queue
Accepted-but-undelivered messages with their next retry time. Every MTA has one; finding which queue a message is in is most of debugging.
Greylisting
Answering a first-time sender with a temporary 4xx on purpose. Real servers retry; most spam bots do not.
IMAP / JMAP / POP3
Protocols for a client to read a mailbox. IMAP is universal, JMAP is its JSON-over-HTTPS successor that Stalwart speaks natively, POP3 downloads-and-deletes.
Sieve
A small filtering language run by the MDA at delivery time: file, flag, forward, discard. ManageSieve is the protocol for editing those rules remotely.
