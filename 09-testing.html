Testing and Troubleshooting, One Layer at a Time

Every fault in this system lives on one of six layers, and each layer has one command that answers "is it this one?" in under a second. This page is those commands, in the order that finds the fault fastest.

Keep this page open during the build. It is the one I will reach for most.

0. The method

The Caddy debugging story in the Homelab series taught me one thing I keep relearning: when something is broken, the temptation is to change a setting and see if it helps. That produces a hope. A targeted command produces a fact, and a fact eliminates a whole layer at once. So the rule here is cheapest fact first: DNS before listeners, listeners before reachability, reachability before TLS, TLS before SMTP, and logs last, because logs are where you go once you know which log to read.

Mail has more layers than a website, and the hops are spread over two machines, so the ladder is longer. But each rung is still one command.

1. Is it DNS?

Most "the mail server is broken" reports from new setups are DNS: a record that has not propagated, a proxied record, a typo in a selector. These are the lookups, with what I expect each to return.

# Who accepts mail for the domain?
dig MX 22112002.xyz +short
# 10 mail.22112002.xyz.

# Where is that host?  (must be the VPS, never a Cloudflare 104.x / 172.x address)
dig A mail.22112002.xyz +short
# <vps-public-ip>

# And does the IP claim the same name back?
dig -x <vps-public-ip> +short
# mail.22112002.xyz.

# SPF, on the bare domain
dig TXT 22112002.xyz +short
# "v=spf1 mx -all"

# DMARC
dig TXT _dmarc.22112002.xyz +short
# "v=DMARC1; p=none; rua=mailto:..."

# DKIM: the selector names come from Stalwart's domain page (Part 07)
dig TXT <selector>._domainkey.22112002.xyz +short
# "v=DKIM1; k=rsa; p=MIIB..."   or   k=ed25519

Two refinements that have each saved me an hour:

  • Ask a specific resolver. dig @1.1.1.1 MX 22112002.xyz asks Cloudflare's public resolver directly, bypassing the router and the ISP. If @1.1.1.1 gives the right answer and the plain command does not, the record is correct and a cache somewhere between me and the internet is stale. Wait for the TTL to expire, or ignore it: the rest of the world is not using my router's cache.
  • Read the TTL. Drop +short and the second column of the answer is the seconds left before a cache has to re-ask. A change I made ten minutes ago with a one-hour TTL is not broken, it is early.
The Cloudflare-specific fault

If dig A mail.22112002.xyz returns two addresses in 104.x.x.x or 172.6x.x.x, the record is proxied (orange cloud). Mail servers connecting to those addresses on port 25 get nothing, and the sender sees a connection timeout. Flip it to DNS only. This is the single most likely DNS mistake in this design, because every other record in the zone is supposed to be orange.

2. Is anything listening?

The same command that cracked the Caddy problem, on both machines. It answers "is a program bound to this port on this address" with no interpretation.

# srv1 — expected Stalwart sockets
sudo ss -tlnp | grep stalwart
# 100.72.72.58:25     smtp, behind HAProxy (PROXY-trusted)
# 100.72.72.58:465    submissions, behind HAProxy
# 100.72.72.58:993    imaps, behind HAProxy
# 127.0.0.1:143       imap for Roundcube, loopback only
# 127.0.0.1:587       submission for Roundcube, loopback only
# 127.0.0.1:8080      http, admin via Tailscale Serve (Part 07)

# VPS — expected HAProxy and Postfix sockets
sudo ss -tlnp | grep -E 'haproxy|master'
# <vps-public-ip>:25      haproxy
# <vps-public-ip>:465     haproxy
# <vps-public-ip>:993     haproxy
# <vps-tailscale-ip>:25   master (postfix)
# 127.0.0.1:25            master (postfix)

The thing to look at is the address column, not just the port. Port 25 appears twice on the VPS on purpose, bound to two different interfaces by two different programs. If HAProxy's line reads 0.0.0.0:25 or *:25, it has grabbed the Tailscale interface too, and Postfix either failed to start or is being shadowed. If a Stalwart listener reads 0.0.0.0 rather than the Tailscale IP, it is reachable from the LAN and I did not mean it to be.

An empty result means the service is not running, and systemctl status <unit> is the next command, not a config change.

3. Can the hops reach each other?

Listening is necessary, not sufficient. The next question is whether the specific pair of machines that need to talk actually can. nc -vz opens a TCP connection and closes it without sending anything, so it tests the network path and nothing else.

# VPS → srv1, the inbound path HAProxy uses
nc -vz 100.72.72.58 25
nc -vz 100.72.72.58 465
nc -vz 100.72.72.58 993

# srv1 → VPS, the outbound path Stalwart's relay route uses
nc -vz <vps-tailscale-ip> 25

# Is the Tailscale link itself up and direct?
tailscale status
tailscale ping 100.72.72.58        # from the VPS
tailscale ping <vps-tailscale-ip>  # from srv1

Reading tailscale ping: a reply via DERP means the two machines are talking through a Tailscale relay server, not directly. It still works, but adds latency and is a sign the VPS firewall is blocking UDP 41641. A reply naming the other machine's real address is a direct connection.

If nc fails but tailscale ping works, the problem is on the destination machine: a firewall there, or the service bound to a different address (back to rung 2). If both fail, it is Tailscale: systemctl status tailscaled and look for Needs login, the exact state from the Homelab Tailscale story.

4. Is TLS right?

openssl s_client opens a TLS connection and prints the certificate chain and the handshake result. Two forms, because the mail ports use TLS two different ways:

# Implicit TLS (465 and 993): TLS from the first byte
openssl s_client -connect mail.22112002.xyz:993 -servername mail.22112002.xyz < /dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName

# STARTTLS (25): plain SMTP first, then upgrade
openssl s_client -connect mail.22112002.xyz:25 -starttls smtp -servername mail.22112002.xyz < /dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName

Four things to check in the output, in order:

  1. Issuer should be Let's Encrypt. A self-signed or "Stalwart" issuer means the ACME step in Part 07 did not complete and the server is using its bootstrap certificate.
  2. Subject Alternative Names must include mail.22112002.xyz. A certificate for the wrong name passes the handshake with s_client but every real client refuses it.
  3. Dates. notBefore in the past, notAfter in the future. The Homelab series has already hit "certificate is not yet valid" because of a clock stuck in the past; timedatectl on the machine that complains is the fix, not the certificate.
  4. Verify return code at the bottom of the unfiltered output should be 0 (ok).

Note that both commands go through HAProxy to srv1, so a correct result here also proves rungs 2 and 3 for the public path in one go.

5. Does SMTP answer properly?

swaks (Swiss Army Knife for SMTP, apt install swaks) has a whole SMTP conversation and prints every line of it. It is the fastest way to see the exact reply code a server gives, which Part 02 explained how to read.

# Inbound: pretend to be another mail server delivering to me, over the public port
swaks --to me@22112002.xyz --from test@example.com --server mail.22112002.xyz:25
# expect 220 banner, 250 after each command, 250 2.0.0 ... queued after DATA

# Authenticated submission: pretend to be my phone sending out
swaks --to someone@gmail.com --from me@22112002.xyz \
      --server mail.22112002.xyz:465 --tls-on-connect \
      --auth LOGIN --auth-user me@22112002.xyz
# prompts for the password; expect 235 after AUTH, then 250 ... queued

# Relay check, from srv1 over Tailscale: Postfix must accept me
swaks --to someone@gmail.com --from me@22112002.xyz --server <vps-tailscale-ip>:25

# Relay check, from the laptop over Tailscale: Postfix must REFUSE me
swaks --to someone@gmail.com --from me@22112002.xyz --server <vps-tailscale-ip>:25
# expect 454 4.7.1 ... Relay access denied

Reading the codes: 2xx is success, 4xx is "not now, try later" and the sender will retry, 5xx is "never" and the sender will bounce. The three-digit code is for machines; the text after it is for me, and Stalwart's and Postfix's text is specific enough to name the rule that fired.

6. Logs, in path order

By the time I am here, the rungs above have told me which hop is at fault, so I read that hop's log and not all five. In the order a message travels:

HopCommandWhat to look for
HAProxy (VPS)sudo journalctl -u haproxy -fOne line per connection: client IP and port, which frontend, which backend, bytes each way. SD/SC termination states and DOWN for the backend mean it could not reach srv1.
Stalwart (srv1)sudo journalctl -u stalwart -f, plus the WebUI's live view and queue pagesThe connecting IP (must match HAProxy's line if PROXY is working), SPF/DKIM/DMARC results on inbound, spam score, and on outbound which route it chose and what the relay replied.
Postfix (VPS)sudo tail -f /var/log/postfix.logstatus=sent with the remote server's 250 line; status=deferred with the 4xx reason (greylisting, rate limits, new-IP suspicion); status=bounced with the 5xx reason. Relay access denied here means a client Postfix does not trust.
Caddy (srv1)sudo journalctl -u caddy --no-pager -n 50Only relevant for Roundcube and the MTA-STS page. Did the request for webmail.22112002.xyz arrive and which block handled it.
PHP-FPM (srv1)sudo journalctl -u php8.4-fpm and Roundcube's own logs/errors.logRoundcube failures. Remember the LMS guide: PHP worker errors are silent unless catch_workers_output = yes is set in the pool config.

The one cross-check worth doing every time: pick a single connection and find it in two adjacent logs by timestamp. The same client IP appearing in HAProxy's line and Stalwart's line is the PROXY protocol proving itself. The same queue ID appearing in Stalwart's outbound log and then Postfix's inbound log is the relay route proving itself.

8. External checkers worth trusting

Everything above is me looking at my own system. These look at it from the outside, which is the view that matters.

  • mail-tester.com: a one-shot score with the deductions explained. Good for a before-and-after on any change to SPF, DKIM or content.
  • mxtoolbox.com: MX lookup, SMTP diagnostics (connects to port 25 and reports banner, STARTTLS, reverse DNS, open relay), and the blacklist check across dozens of lists. Run the blacklist check on the day the VPS is rented.
  • learndmarc.com: send a message, watch it evaluate SPF, DKIM and DMARC live with every DNS lookup shown. The best explanation of a failure I have found.
  • hardenize.com or internet.nl: the transport-security view: MTA-STS, TLS-RPT, DANE, DNSSEC, TLS versions. Expect DANE to be red until DNSSEC is on for the zone, which is a later project.
  • Google Postmaster Tools: once there is real volume to Gmail, this shows how Google rates the domain and IP over time. Needs the domain verified; worth setting up in the first week so there is history when something changes.

9. The five-minute routine after any change

Once the build is done, most faults will come from me changing something: a DNS record, a listener, a Postfix line, an upgrade. Rather than wait for a bounce to tell me, I run the first five rungs in one go after every change. This is not a monitoring system; it is the ladder, scripted, so that I cannot skip a rung because I was sure it was fine.

#!/usr/bin/env bash
# mailcheck.sh — run from the laptop, on any network. Replace the placeholders once.
set -u
D=22112002.xyz; H=mail.$D; IP=<vps-public-ip>

echo "== 1 DNS";        dig +short MX $D; dig +short A $H; dig +short -x $IP
echo "== 1 SPF/DMARC";  dig +short TXT $D; dig +short TXT _dmarc.$D
echo "== 3 reach";      for p in 25 465 993; do nc -vz -w 5 $H $p 2>&1 | tail -1; done
echo "== 4 TLS 993";    openssl s_client -connect $H:993 -servername $H </dev/null 2>/dev/null \
                          | openssl x509 -noout -subject -enddate
echo "== 4 TLS 25";     openssl s_client -connect $H:25 -starttls smtp -servername $H </dev/null 2>/dev/null \
                          | openssl x509 -noout -subject -enddate
echo "== 5 SMTP";       swaks --quit-after RCPT --to me@$D --from check@example.com --server $H:25 2>&1 \
                          | grep -E '^<[\*-] (220|250|4|5)' | head -5

Reading it takes thirty seconds: three DNS answers that agree, two TXT records, three succeeded lines, two certificates with the right name and a future date, and a column of 250s. Anything else names the rung, and the matching section above says what to do.

The one rung it cannot climb is 6: it does not read logs, by design. If the script is green and mail still does not arrive, the fault is inside Stalwart or Postfix and the logs table is the next stop.

Keep the output

Save a known-good run as mailcheck.good.txt. The next time something breaks, diff against it shows exactly which line changed, which is usually the whole diagnosis.

Glossary for this part

Rung
One layer of the system with one command that confirms or eliminates it. Six rungs here.
dig
The DNS lookup tool. +short prints only the answer; @1.1.1.1 asks a specific resolver; -x does a reverse lookup.
ss -tlnp
Lists listening TCP sockets with the program that owns each one. The address column matters as much as the port.
nc -vz
Opens and immediately closes a TCP connection, reporting whether it succeeded. Tests the path, not the protocol.
openssl s_client
Makes a TLS connection by hand and shows the certificate and handshake. -starttls smtp for port 25, plain for 465 and 993.
swaks
A command-line SMTP client that prints the whole conversation. The quickest way to see a server's exact reply code.
DERP
Tailscale's relay servers, used when two machines cannot connect directly. Working but slower; usually means a UDP port is blocked.
Termination state
The two-letter code in an HAProxy log line saying how and why the connection ended. -- is normal; anything with S or C first is the server or client side closing unexpectedly.
