Part 09 · Keeping it working

Testing and Troubleshooting, One Hop at a Time

A message to me now crosses Gmail, Cloudflare's MX, a Worker, my tunnel and Stalwart. A message from me crosses Roundcube, Stalwart, Resend and the recipient's MX. Each hop has exactly one place that tells the truth about it. This page is the list, in the order that finds the fault fastest.

Rewritten after the build on 8 October 2026. The faults table is what actually happened, not what I guessed might.

0. The method

The Caddy debugging story in the Homelab series taught me one thing I keep relearning: when something is broken, the temptation is to change a setting and see if it helps. That produces a hope. A targeted command produces a fact, and facts stack. Mail has more hops than a website and three of them belong to other people, so the ladder is longer and two rungs are read in someone else's dashboard rather than my own shell. But each rung is still one look.

1. Is it DNS?

The zone has two owners now besides me, so the first question is whether each of them still has what it needs. My laptop has no dig, so on build day I queried Cloudflare's resolver over HTTPS; dig works the same if it is installed.

# one function, any record
q(){ curl -s "https://cloudflare-dns.com/dns-query?name=$1&type=$2" -H 'accept: application/dns-json' \
  | python3 -c 'import sys,json; a=json.load(sys.stdin).get("Answer"); print(" | ".join(x["data"] for x in a) if a else "(none)")'; }

q 22112002.xyz MX                      # must be route1/2/3.mx.cloudflare.net, nothing else
q 22112002.xyz TXT                     # must contain v=spf1 include:_spf.mx.cloudflare.net ~all
q cf2024-1._domainkey.22112002.xyz TXT  # Cloudflare's DKIM key
q resend._domainkey.22112002.xyz TXT    # Resend's DKIM key, p=MIGf…
q rsend.22112002.xyz CNAME             # rsend-euw1.forge.rmta.net
q _dmarc.22112002.xyz TXT              # v=DMARC1; p=…
q mail.22112002.xyz A                  # Cloudflare's proxy IPs: it is a tunnel hostname now

Expected answers are in the comments. The one that bites is the MX: if anything other than Cloudflare's three hosts appears, Stalwart's DNS management has been re-enabled for MX, or someone added a record by hand, and inbound mail is going somewhere that cannot speak SMTP. If the resolver seems to lie, remember the records have a five-minute TTL; on build day I polled for five minutes before concluding a record really was still there, and it was.

2. Did Cloudflare receive it?

Cloudflare dashboard, the domain, Email › Email Routing › Activity log. Every message to the domain appears with a status. Delivered to the Worker is the good one. Dropped with an error means the Worker threw or rejected, which rung 3 explains. Rejected at Cloudflare's own edge means their spam or policy check refused it before any of my code ran. If the message is not in this log at all, the sender never reached Cloudflare: back to rung 1, or check the sender's own queue.

Also worth a look on the same page: Routing rules, where the catch-all must read "Send to a Worker: mail-inbound-bridge" and be Active. It is the single switch between "mail arrives" and "mail vanishes".

3. Did the Worker get through the tunnel?

cd ~/Projects/mailserver/worker
npx wrangler tail mail-inbound-bridge --format pretty

Leave it running and send a test. The healthy line is the one from build day:

Email from:…@gmail.com to:olwethu@22112002.xyz size:6962 @ 10/8/2026, 4:09:41 PM - Ok

An exception in the output means the Worker could not complete the SMTP session. The two reasons I would expect: the tunnel on srv1 is down (the VPC stream simply ends, and the Worker reports "SMTP connection closed before a complete reply"), or Stalwart answered with a 4xx or 5xx. A 5xx becomes a rejection that the original sender sees as a bounce. For the tunnel: systemctl status cloudflared on srv1, and https://webmail.22112002.xyz from the laptop, which uses the same tunnel and is the fastest proof it is up.

To separate "Worker cannot reach Stalwart" from "Stalwart refuses the message", run the Worker's job by hand on srv1:

python3 - <<'EOF'
import smtplib, email.utils
msg = f"From: Loopback Test <someone@example.org>\nTo: olwethu@22112002.xyz\nSubject: loopback test\nDate: {email.utils.formatdate()}\nMessage-ID: {email.utils.make_msgid(domain='example.org')}\n\nhello\n"
s = smtplib.SMTP("127.0.0.1", 25, timeout=20); s.ehlo("gmail.com")
print(s.sendmail("someone@example.org", ["olwethu@22112002.xyz"], msg)); s.quit()
EOF

If that prints {} and the message lands in Spam (it is unsigned mail claiming someone else's domain, so Spam is correct), Stalwart's side is fine and the fault is between the Worker and the tunnel.

4. What did Stalwart do with it?

Stalwart logs to a dated file, not the journal, with colour codes that need stripping. This is the one grep I used all day:

sudo sed 's/\x1b\[[0-9;]*m//g' /var/log/stalwart/stalwart.$(date +%F) \
  | grep -E 'listenerId = "smtp"|queueName|message-ingest|dkim|dmarc|deliver|connect' \
  | grep -v DEBUG | tail -40

For an inbound message the healthy sequence is: smtp.spf-ehlo-fail and smtp.spf-from-fail (soft fail against 127.0.0.1, always, ignore), smtp.iprev-pass, smtp.dkim-pass with the sender's domain, smtp.dmarc-pass, message-ingest.ham, delivery.completed. For an outbound message: queue.authenticated-message-queued on the submissions listener, then delivery.connect with hostname = "smtp.resend.com", delivery.delivered with code = 250 and a Resend id, delivery.completed.

Two things the log will not tell you. A settings reload leaves no line, so if a route or strategy change seems ignored, assume the reload has not happened and run Management › Actions › Reload › Server settings again. And an outbound attempt that shows hostname = "gmail-smtp-in.l.google.com" and then delivery.connect-error after about 270 seconds is the strategy still saying 'mx'; nothing at home can complete that connection.

The queue itself is visible in the admin under Management › Emails › Queued, with retry times, and stuck messages can be deleted there.

5. Did Resend deliver it?

resend.com, left menu Logs (or Emails). Every message Stalwart handed over appears with Resend's id, the one from Stalwart's delivery.delivered line, and its own status: delivered, bounced, or complained. A message that Stalwart shows as 250 but Resend shows as bounced was refused by the final recipient's server, and Resend's entry has their reply. Also on this site: Domains must still show 22112002.xyz as Verified, and the day's count against the 100-a-day cap.

6. What did the recipient decide?

In Gmail, open the message, the three-dot menu, Show original. The summary block at the top has three lines that matter: SPF should say PASS with Resend's sending host, DKIM should say PASS with d=22112002.xyz (there may be two signatures, Stalwart's and Resend's, both for the domain), and DMARC should say PASS. If DMARC fails while DKIM passes, alignment is broken: the From address is not at 22112002.xyz, or Resend's key is missing from DNS. If the message landed in Spam with all three passing, it is content or reputation, not authentication; mail-tester.com will say which.

8. External checkers worth trusting

  • mail-tester.com: a one-shot score with the deductions explained. Send to the address it gives from Roundcube; the message goes through Resend like any other, so the score reflects what recipients see.
  • learndmarc.com: send a message, watch it evaluate SPF, DKIM and DMARC live with every DNS lookup shown. The clearest explanation of an alignment failure I have found.
  • mxtoolbox.com: the MX lookup should show Cloudflare's three hosts; the SMTP diagnostic against them is Cloudflare's problem, not mine, which is the point.
  • Google Postmaster Tools: once there is real volume to Gmail, this shows how Google rates the domain over time. The IP reputation shown will be Resend's.

9. The five-minute routine after any change

Most faults will come from me changing something: a DNS record, a route, a Caddy block, an upgrade of Stalwart or the Worker. Rather than wait for a bounce to tell me, I run the first rungs that need no dashboard in one go:

#!/usr/bin/env bash
# mailcheck.sh — run from the laptop, on any network.
set -u
D=22112002.xyz
q(){ curl -s "https://cloudflare-dns.com/dns-query?name=$1&type=$2" -H 'accept: application/dns-json' \
  | python3 -c 'import sys,json; a=json.load(sys.stdin).get("Answer"); print(" | ".join(x["data"][:70] for x in a) if a else "(none)")'; }
echo "MX      $(q $D MX)"
echo "SPF     $(q $D TXT)"
echo "CF DKIM $(q cf2024-1._domainkey.$D TXT | cut -c1-40)"
echo "RS DKIM $(q resend._domainkey.$D TXT | cut -c1-40)"
echo "rsend   $(q rsend.$D CNAME)"
echo "DMARC   $(q _dmarc.$D TXT)"
echo "JMAP    $(curl -s -o /dev/null -w '%{http_code}' https://mail.$D/.well-known/jmap)   (want 307)"
echo "admin   $(curl -s -o /dev/null -w '%{http_code}' https://mail.$D/admin)   (want 403)"
echo "webmail $(curl -s -o /dev/null -w '%{http_code}' https://webmail.$D/)   (want 200)"
ssh srv1@srv1 'systemctl is-active stalwart cloudflared caddy php8.4-fpm | tr "\n" " "; echo; free -h | sed -n 2p'

Save a known-good run and diff against it. The first line that differs is the rung to start on.

Glossary for this part

Activity log (Email Routing)
Cloudflare's per-message record of what it received for the domain and what it did with it. Rung 2.
wrangler tail
Live stream of a Worker's console output and the result of each invocation. Rung 3.
Loopback simulation
Doing the Worker's SMTP conversation by hand from srv1 to 127.0.0.1:25, to prove Stalwart's half without involving Cloudflare.
DoH query
A DNS lookup over HTTPS to cloudflare-dns.com/dns-query; the same answers as dig @1.1.1.1 on a machine without dig.
Show original
Gmail's view of a received message's raw headers with its SPF, DKIM and DMARC verdicts summarised at the top. Rung 6.
Reload server settings
The Stalwart action without which a saved route or strategy is just a saved form.
