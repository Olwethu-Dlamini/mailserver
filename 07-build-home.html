Build Part 1: Everything at Home

Every piece that lives on srv1, installed and proven over Tailscale before a single cent went to a VPS provider. It took one morning and one afternoon, and almost nothing went the way the plan said.

Each step ends with a checkpoint: the command, or the log line, that proved the step worked. Where I skipped a checkpoint and paid for it, I say so.
How this page came to be

I wrote this page as a plan on the morning of 8 October 2026, from Stalwart's documentation for v0.16 and from how the rest of srv1 is set up. Then I did the build, keeping a raw log of every command and every surprise in notes/build-log-2026-10-08.md in the repo. The same afternoon I rewrote the page from that log. What follows is what happened, in the order it happened, wrong turns included. The one rule that carried me through, as in every other part of this homelab: prefer a command that produces a fact over a change that produces a hope.

0. What this part built

The order mattered. Stalwart had to exist before the domain could be configured; the domain had to be linked to a DNS provider before a certificate could be issued; accounts needed the domain; Roundcube needed accounts to log in with. Each checkpoint was the input to the next, and the one time I did not check (the certificate, step 7) I lost twenty minutes.

1. Pre-flight, and two problems before the first command

The plan said "collect five facts". The facts were fine. Getting into a position to collect them was not.

Getting a shell at all

I drive these builds from the laptop, with commands run over SSH so the output lands next to the notes. This laptop had no SSH key. Generating one takes a second:

ssh-keygen -t ed25519 -N "" -C "oll@omarchy" -f ~/.ssh/id_ed25519

Getting it onto srv1 was the problem. ssh-copy-id needs to type the password, and it was being run from a prompt that has no terminal attached, so it failed with ssh_askpass: exec(/usr/lib/ssh/ssh-askpass): No such file or directory. Fine, paste the key into authorized_keys by hand from the console I already had open on the server. That broke twice: the key is 68 characters of base64, the terminal wrapped the line, and the wrap landed inside the single quotes, so bash saw an unterminated string and a stray newline. What finally worked was refusing to have any long line at all:

mkdir -p ~/.ssh && chmod 700 ~/.ssh
K=AAAAC3NzaC1lZDI1NTE5AAAAIKOX5RZJhvMUwgwXjNdmPsUSIDLowgm16/4g+XCygZcU
echo "ssh-ed25519 $K oll@omarchy" >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys && wc -l ~/.ssh/authorized_keys

Four lines, each short enough that nothing wraps. The lesson generalises: when pasting into a remote shell, the paste is only as reliable as the longest line in it.

sudo wants a password

The second blocker: sudo -n true said a password is required, so nothing could be scripted. I chose to let my user run sudo without a password for the length of the build. Same line-wrap problem: the first paste ran sudo with no arguments (the wrap landed right after it) and printed the usage text. Second attempt:

echo 'srv1 ALL=(ALL) NOPASSWD: ALL' | sudo tee /etc/sudoers.d/srv1-nopasswd
sudo chmod 440 /etc/sudoers.d/srv1-nopasswd
sudo visudo -c        # must say: parsed OK
Undo this later

Passwordless sudo is a convenience for a build session, not a permanent state. sudo rm /etc/sudoers.d/srv1-nopasswd puts it back.

2. A Cloudflare API token, scoped tightly

The plan gave this one line. It deserves eleven, because the dashboard path is not obvious and the wrong token is dangerous.

  1. Log in at dash.cloudflare.com.
  2. Click the profile icon top right, then My Profile.
  3. Left menu: API Tokens.
  4. Create Token.
  5. Find the template Edit zone DNS and click Use template.
  6. Permissions: the prefilled row is Zone / DNS / Edit. Click + Add more and add Zone / Zone / Read, so Stalwart can look up the zone by name.
  7. Zone Resources: Include / Specific zone / 22112002.xyz. Not "All zones".
  8. Leave client IP filtering and TTL empty.
  9. Continue to summary, confirm it says DNS Edit and Zone Read on one zone, then Create Token.
  10. The token is shown once. Copy it into the password manager immediately.
  11. Cloudflare shows a curl verify command under it; running it should return "status": "active".
Not the Global API Key

Further down the same page is the account's Global API Key. It can do anything to every zone and every setting in the account. A mail server needs to edit one zone's DNS records and nothing else. If the scoped token ever leaks, the damage is bounded to this domain's DNS; if the global key leaks, it is not.

Checkpoint 2
  • A token in the password manager. It is not used until step 5, and it was never pasted anywhere but the Stalwart form.

3. Install Stalwart

The official installer is a shell script. Before running something as root from the internet I read what it touches:

cd /tmp

grep -nE "useradd|mkdir|systemctl|/etc/stalwart|/var/lib/stalwart|https://" install.sh

1069 lines. It downloads the latest release from github.com/stalwartlabs/stalwart/releases, creates a stalwart system user with no shell, makes the directories, writes an environment file, installs a systemd unit, enables it and starts it. Nothing surprising.

Surprise one: still in bootstrap mode

The docs say that after the wizard Stalwart "restarts into normal operation". It did not. config.json had been written:

{"@type":"RocksDb","path":"/var/lib/stalwart/","blobSize":16834,"bufferSize":134217728,"poolWorkers":null,"cacheSize":134217728}

but ss -tln still showed only *:8080 and the log said nothing after the login. A manual restart fixed it:

sudo systemctl restart stalwart
ss -tln | grep -vE ':(22|80|3306)\s'
*:25   *:465   *:993   *:995   *:4190   *:443   *:8080

Those are the default listeners for a fresh 0.16 install: SMTP, submissions, IMAPS, POP3S, ManageSieve, HTTPS and the HTTP admin port. Note what is not there: no 143, no 587, no 110. Only the implicit-TLS variants of each protocol. That matters in step 8.

Verify

Whether the missing self-restart is the documented behaviour, a quirk of running under systemd, or something I clicked past, I don't know. The symptom is unambiguous though: if config.json exists and the only listener is 8080, restart the service.

Surprise two: the log is not in the journal

journalctl -u stalwart shows only the startup banner. Everything else goes to /var/log/stalwart/stalwart.YYYY-MM-DD, with ANSI colour codes embedded, which makes grep painful. The one-liner I used all day:

sudo sed 's/\x1b\[[0-9;]*m//g' /var/log/stalwart/stalwart.2026-10-08 | grep -iE 'acme|dns|auth\.' | tail

What the first normal-mode start logged, in order: MTA queue started; task scheduler started with purge and spam-classifier training tasks; two DKIM keys created for 22112002.xyz, v1-ed25519-20261008 and v1-rsa-20261008; spam filter rules loaded (66 rules, 18 DNSBL servers, 403 tags); then two warnings worth understanding:

  • The configured DNS resolver cannot validate DNSSEC. DANE has been disabled to avoid deferring mail. The VM's resolver is Tailscale's MagicDNS at 100.100.100.100, which does not do DNSSEC validation. DANE is the optional check from part 03; losing it on outbound costs nothing here because outbound will leave via the relay anyway.
  • No TLS certificates available, total = 0. Expected until step 7. In the meantime the listeners serve a placeholder: CN=rcgen self signed cert, valid from 1975 to 4096.

So the wizard had quietly done more than it said: the domain object existed and DKIM was already generated. Step 7 was editing, not creating.

Surprise three: locked out of the admin

Logging in at :8080/admin with the generated password failed, repeatedly. The temptation was to assume a wrong password and go hunting for a reset. The log said otherwise:

ERROR Authentication error (auth.error) listenerId = "http", localPort = 8080,
      remoteIp = 100.89.10.41, reason = "Failed to decode token. ..."

"Failed to decode token" is not "wrong password". The browser still held the session token from the bootstrap login, the bootstrap account no longer existed, and the UI kept replaying the dead token before ever sending the new credentials. Fix: a private window. The generated password worked first time. The permanent account, I learned from the next log line, is admin@22112002.xyz, not plain admin.

6. Tell Stalwart how to get certificates

Settings › TLS › ACME Providers › Add. The Directory is prefilled with https://acme-v02.api.letsencrypt.org/directory, Let's Encrypt production; leave it. The field that matters is Challenge type, which defaults to TlsAlpn01 and must be changed to Dns01. TLS-ALPN proves ownership by answering on port 443 from the internet; HTTP-01 does the same on port 80. Neither port can be reached at my house (part 01), so neither can ever succeed here. DNS-01 proves ownership by writing a TXT record, which needs no inbound port at all, only the DNS provider from step 5. Contact: a real email address, where Let's Encrypt sends expiry warnings. Everything else at default. Save.

A question that came up at this point, and is worth answering because the Cloudflare dashboard makes it confusing: the domain already has SSL, so why is this needed? Because Cloudflare's certificate covers web traffic passing through Cloudflare's edge. Mail clients and other mail servers connect straight to Stalwart on 465, 993 and 25, and Stalwart has to present its own certificate on those connections. Cloudflare is not in that path.

Checkpoint 6
  • The provider appears in the list with challenge type Dns01. Again, the real proof is the certificate in step 7.

The trap: a second dropdown, two sections up

I saved the domain, watched the records appear, waited for the certificate, and nothing happened. For twenty minutes. No _acme-challenge record in DNS, no ACME lines in the log, only the same No TLS certificates available warning repeated at every settings reload. 8. Listeners: the step that disappeared

The plan had a whole step here: rebind the public-facing listeners to the Tailscale IP, add loopback listeners on 143 and 587 for Roundcube, move the admin UI behind tailscale serve. None of it was needed today.

The fear behind the plan was this: in part 08 the listeners on 465 and 993 will trust the VPS to send a PROXY protocol header with the real client address. I assumed a listener that trusts PROXY would require it from everyone, so Roundcube on loopback would need its own untrusted listeners on 143 and 587. The NetworkListener reference says otherwise: overrideProxyTrustedNetworks "enables proxy protocol for connections from these networks". A connection from 127.0.0.1 is not from the VPS's network, so it is treated as an ordinary connection. One set of listeners serves both the front door and the webmail.

So Roundcube points at the ports that already exist, with implicit TLS, and the wildcard certificate verifies against the hostname even though the connection goes to an IP:

for p in 993 465 4190; do
  echo | openssl s_client -connect 127.0.0.1:$p -servername mail.22112002.xyz \
    -verify_hostname mail.22112002.xyz -verify_return_error 2>/dev/null | grep Verification
done
Verification: OK

Verification: OK

Rebinding 25, 465 and 993 to the Tailscale address, and moving the admin behind tailscale serve, are deferred to part 08. They are tidiness, and today was for things that produce a working mailbox.

The lesson I did not plan to learn today

The first two messages I sent from that inbox went to a Gmail address and to an address at a local ISP, before the relay existed. Part 01 says, in theory, that mail cannot leave from behind CGNAT. Here is what it looks like in practice:

10:57:17 Queued message submission for delivery   listenerId = "submissions", localPort = 465
10:57:17 Delivery attempt started                 domain = "gmail.com"
10:57:18 Fetched MTA-STS policy, Host authorized by MTA-STS policy
10:57:18 TLSA record not DNSSEC signed            (DANE off, as warned)
…
10:58:39 Connection error (delivery.connect-error) domain = "realnet.co.sz", elapsed = 133790ms
10:58:39 Message rescheduled (queue.rescheduled)  nextRetry = +2 min, nextDsn = +24 h

Stalwart did everything right: looked up the MX, fetched the receiving domain's MTA-STS policy and TLS-RPT address, tried to connect on port 25, and waited 133 seconds for a SYN that was never answered. A quick check confirmed why:

nc -vz gmail-smtp-in.l.google.com 25      # nothing, for 8 seconds, then timeout

Outbound port 25 is filtered on this ISP. Not even "sending works, receiving doesn't": nothing on 25 leaves the house in either direction. The messages would have retried every few minutes and bounced back into my own inbox after 24 hours (nextDsn). I deleted both under Management › Emails › Queued. They get sent for real in part 08.

12. Backups, before there is anything worth losing

Everything that makes this server what it is lives in four places: /etc/stalwart/config.json, /etc/stalwart/stalwart.env, /var/lib/stalwart/ (the RocksDB store: accounts, settings, DKIM keys, certificates, every message), and Roundcube's config plus its small database. A script, a systemd timer, done while waiting for the certificate:

#!/bin/sh
# /usr/local/sbin/stalwart-backup
set -e
umask 077
DEST=/var/backups/stalwart; STAMP=$(date +%F)
tar -czf "$DEST/stalwart-$STAMP.tgz" /etc/stalwart/config.json /etc/stalwart/stalwart.env \
  /var/lib/stalwart /var/www/webmail.22112002.xyz/config/config.inc.php
mariadb-dump --single-transaction roundcubemail | gzip > "$DEST/roundcube-$STAMP.sql.gz"
find "$DEST" -name '*.tgz' -mtime +14 -delete
find "$DEST" -name '*.sql.gz' -mtime +14 -delete
# stalwart-backup.timer:  OnCalendar=*-*-* 03:30:00  Persistent=true
sudo systemctl enable --now stalwart-backup.timer
sudo systemctl start stalwart-backup.service && sudo ls -l /var/backups/stalwart

Two corrections after the first run. The archives came out world-readable and contain the Roundcube database password, so the directory went to mode 700 and the script got umask 077. And a RocksDB directory copied while Stalwart is running is a reasonable snapshot but not a guaranteed-consistent one; for a restore that matters, stop the service first. The destination is still the same spinning disk as everything else, which the RAM-upgrade post already flagged; copying the archive off the box is the next improvement, not today's.

Checkpoint 12
  • First run: stalwart-2026-10-08.tgz 751 KB and roundcube-2026-10-08.sql.gz 3 KB, mode 600, in a 700 directory.
  • systemctl list-timers stalwart-backup.timer: next run 03:30 tomorrow.

13. Deliberately not done yet

A working mail system that only I can reach. These are the pieces that make it reachable by the world, and they are all part 08 because they all need the VPS to exist first:

  • An A record for mail.22112002.xyz pointing at <vps-public-ip>, grey cloud. Every record Stalwart published today points at this name, and today it points nowhere.
  • A PTR record at the provider, mapping <vps-public-ip> back to mail.22112002.xyz.
  • HAProxy on the VPS forwarding 25, 465 and 993 to 100.72.72.58 with PROXY protocol v2.
  • The overrideProxyTrustedNetworks value on those three listeners.
  • A Postfix relay on the VPS and a Stalwart Relay route so outbound mail leaves from the VPS's IP. The two deleted messages are the first test.
  • Confirming the SPF record covers the VPS IP (it uses mx, which resolves to it once the A record exists).
  • The first real message to Gmail, and reading its headers.

And two items that came out of today rather than the plan:

  • Lower DMARC to p=none before any mail leaves, then walk it up as part 03 describes.
  • Optionally bind 25, 465 and 993 to 100.72.72.58 instead of every interface, and put the admin UI behind tailscale serve. Hygiene, not a blocker.

Until then the domain receives nothing from outside, and that is by design: there is no point exposing a mail server to the internet before proving, privately, that it does what I think it does. Today it did.

Glossary for this part

Bootstrap mode
Stalwart's first-start state when no config.json exists: web UI only on port 8080, a one-time admin password in the journal, no mail services until the wizard finishes and, in my case, until a manual restart.
Checkpoint
A command whose output proves a step worked. The discipline of not moving on without one. Step 7 is what happens when you skip it.
DNS-01
The ACME challenge where ownership of a name is proven by writing a TXT record, so no port needs to be reachable from the internet. The only challenge type that can work from behind CGNAT.
Wildcard certificate
One certificate for *.22112002.xyz, valid for any single-label name under the zone. Only obtainable with DNS-01. Stalwart requests one when the domain's subject alternative names are left empty.
DnsServer / ACME provider
Stalwart's names for "credentials to edit a DNS zone" and "which certificate authority to ask, with which challenge". A domain links to both, through two separate dropdowns in two sections of its form.
Stale token
A browser session cookie from an account that no longer exists. The symptom is "Failed to decode token" in the log, and the cure is a private window, not a password reset.
overrideProxyTrustedNetworks
Per-listener list of proxies allowed to send a PROXY protocol header with the real client address. It applies only to connections from those addresses, which is why loopback connections on the same port stay ordinary.
peer_name
The hostname PHP checks a TLS certificate against. Lets Roundcube connect to 127.0.0.1 and still verify a certificate issued for mail.22112002.xyz.
nextDsn
The moment Stalwart gives up on a queued message and sends a delivery status notification (a bounce) back to the sender. 24 hours by default.
DNS-over-HTTPS
Asking a resolver over HTTPS instead of UDP port 53. cloudflare-dns.com/dns-query with a JSON accept header is a usable dig on a machine that has none.
