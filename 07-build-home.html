Build Part 1: Everything at Home

Every piece that lives on srv1, installed and proven over Tailscale before a single cent goes to a VPS provider. If this part works, part 08 is only plumbing.

Each step ends with a checkpoint: the command whose output proves the step worked. Don't move on without it. That rule has saved me more time than any other in this homelab.
This page is the plan

I wrote this before doing the build, from Stalwart's documentation for v0.16 and from how the rest of srv1 is set up. Once I have actually done it, this page gets corrected with what really happened, including the wrong turns, in the same spirit as the Caddy debugging story in the Homelab series. Anything marked verify is a detail I could not confirm from the docs alone.

0. What this part builds

The order matters. Stalwart has to exist before the domain can be added; the domain has to exist before certificates and DKIM can be issued; accounts need the domain; Roundcube needs accounts to log in with. Each step's checkpoint is the input to the next.

1. Pre-flight on srv1

Five facts to collect before installing anything, because every one of them has bitten this homelab before.

Resources

free -h
df -h /

Stalwart idles around 100 MB and the docs say 1 GB is plenty for a handful of users, so on a 4 GB VM already running Caddy, PHP-FPM and MariaDB there is room. Disk is the one to watch: mailboxes grow and everything is still on one spinning HDD. Note the free space now so there's a baseline.

Hostname

A mail server introduces itself by name in every SMTP conversation (the EHLO line, part 02), and that name should be mail.22112002.xyz. Stalwart asks for it in the wizard, so the OS hostname does not strictly have to match, but having the machine agree with itself removes a whole class of confusion.

hostnamectl
sudo hostnamectl set-hostname mail.22112002.xyz
# and make the machine able to resolve its own name without asking the internet:
echo "127.0.1.1 mail.22112002.xyz mail" | sudo tee -a /etc/hosts

The clock

TLS certificates have validity windows and DKIM signatures carry timestamps. A wrong clock produced the "certificate not yet valid" error back when I set up the tunnel, and it will produce stranger errors here.

timedatectl          # want: System clock synchronized: yes
sudo timedatectl set-ntp true

Tailscale address

tailscale ip -4      # expected 100.72.72.58
tailscale status

Ports

Stalwart will want 25, 465, 993, 143, 587 and 8080. Nothing should be on them yet. Caddy is on 80, which is fine.

sudo ss -tlnp | grep -E ':(25|465|993|143|587|8080)\b'
Checkpoint 1
  • timedatectl says synchronized: yes.
  • hostnamectl shows mail.22112002.xyz and getent hosts mail.22112002.xyz returns 127.0.1.1.
  • tailscale ip -4 prints 100.72.72.58.
  • The ss command prints nothing: all six ports are free.

2. A Cloudflare API token, scoped tightly

Two of Stalwart's best features, publishing DNS records for me and getting certificates without any open port, both work by editing the Cloudflare zone through its API. That needs a token. Cloudflare offers a "Global API Key" that can do anything to every zone on the account. Not that one.

In the Cloudflare dashboard: profile → API Tokens → Create Token → Create Custom Token:

  • Permissions: Zone › DNS › Edit, and Zone › Zone › Read.
  • Zone Resources: Include › Specific zone › 22112002.xyz.
  • Leave client IP filtering off for now; srv1 has no fixed public IP to filter on.

The token is shown once. It goes into the password manager immediately, under a name that says what it is for, because in six months "cf-token-2" means nothing. It is pasted into Stalwart in step 5 and nowhere else.

Checkpoint 2
  • Cloudflare's own verify call succeeds from srv1: curl -s -H "Authorization: Bearer $TOKEN" https://api.cloudflare.com/client/v4/user/tokens/verify returns "status":"active".

3. Install Stalwart

Stalwart's installer puts a single binary at /usr/local/bin/stalwart, data under /var/lib/stalwart/, logs under /var/log/stalwart/, and registers a systemd unit. I'm fetching the script to a file before running it, so I can read it first.

curl --proto '=https' --tlsv1.2 -sSf https://get.stalw.art/install.sh -o install.sh
less install.sh
sudo sh install.sh

The bootstrap password

On first start there is no /etc/stalwart/config.json, so Stalwart comes up in bootstrap mode: no mail services, just the web UI on port 8080, and a temporary admin account whose password is printed once to the log. Two ways to get it:

# Option A: read it from the journal (printed exactly once, at first start)
sudo journalctl -u stalwart -n 200 | grep -A8 'bootstrap mode'
# Option B: decide it yourself before first start, with a systemd drop-in
sudo systemctl edit stalwart
# in the editor, add:
#   [Service]
#   Environment=STALWART_RECOVERY_ADMIN=admin:choose-a-temporary-password
sudo systemctl daemon-reload
sudo systemctl restart stalwart

systemctl edit creates an override file under /etc/systemd/system/stalwart.service.d/ without touching the unit the installer wrote, so upgrades won't clobber it. Remove the drop-in once the wizard is done; the temporary account stops working after setup anyway.

Opening the UI, privately

From the laptop, over Tailscale: http://100.72.72.58:8080/admin. This is plain HTTP, which is fine only because the connection is inside the WireGuard tunnel Tailscale provides. Nothing about this URL is reachable from the public internet; there is no port forward, no tunnel ingress, no DNS record.

The UI downloads itself

Stalwart fetches its web UI bundle from GitHub on first start. If srv1 cannot reach GitHub over HTTPS, /admin returns 404 and it looks broken. Check curl -sI https://github.com | head -1 before suspecting anything else.

Checkpoint 3
  • systemctl status stalwart is active (running).
  • sudo ss -tlnp | grep 8080 shows stalwart listening.
  • The admin login page renders in the laptop's browser at http://100.72.72.58:8080/admin and the bootstrap credentials get in.

4. The setup wizard

The wizard writes config.json, which in Stalwart's model is tiny: it only says where the database is. Everything else, listeners, domains, accounts, TLS, lives in that database and is edited through the UI or CLI (part 04 explains why). My answers:

Wizard asksAnswerWhy
Server hostnamemail.22112002.xyzThe name in EHLO, in the certificate, in the MX record and in the PTR record. All four must agree.
Default domain22112002.xyzThe part after the @.
Storage backendRocksDB, /var/lib/stalwart/Embedded, zero extra services, right for one node. Backing it up is backing up a directory.
DirectoryInternalAccounts live in Stalwart itself. No LDAP, no SQL user table to maintain.
Administrator passwordLong, from the password managerThis becomes the permanent admin. The bootstrap one dies on restart.

Keeping the admin reachable after the wizard

After the wizard Stalwart restarts into normal operation, moves the admin UI to https://<hostname>/admin, and stops serving administration on 8080. For most people that's an improvement. For me it's a problem: mail.22112002.xyz will resolve, in public DNS, to the VPS, and I do not want HTTPS on 443 open at the front door just to reach an admin page.

The plan: keep a plain HTTP listener bound to loopback only, and let Tailscale publish it inside the tailnet with a real certificate.

  1. In the UI: Settings › Network › Listeners. Make sure there is an http listener bound to 127.0.0.1:8080. If the wizard removed it, add one.
  2. On srv1: 
    sudo tailscale serve --bg http://127.0.0.1:8080
tailscale serve status
  3. From the laptop: https://srv1.<tailnet>.ts.net/admin. Tailscale terminates HTTPS with a Let's Encrypt certificate it obtains for the MagicDNS name, and only tailnet members can connect.
Verify at build time

Two things I could not confirm from the docs: the exact screens and order of the wizard, and whether a 127.0.0.1:8080 HTTP listener survives the wizard or has to be re-added. Also, tailscale serve requires HTTPS certificates to be enabled for the tailnet in the Tailscale admin console (DNS → HTTPS Certificates); if the serve command complains, that's where to look.

Checkpoint 4
  • cat /etc/stalwart/config.json exists and names /var/lib/stalwart/.
  • journalctl -u stalwart -n 50 shows a normal start, no "bootstrap mode".
  • https://srv1.<tailnet>.ts.net/admin loads with a valid certificate and the permanent admin password works.

5. Tell Stalwart it may edit the zone

Settings › Network › DNS › DNS Providers → add → Cloudflare. Paste the token from step 2. Give the provider an id I'll recognise later, such as cloudflare. This creates what Stalwart calls a DnsServer object: a provider type plus credentials, which domains can then point at.

Checkpoint 5
  • The provider saves without an authentication error. Nothing is in the zone yet; that happens when the domain is added.

6. Tell Stalwart how to get certificates

Settings › TLS › ACME Providers → add. Let's Encrypt, challenge type DNS-01, contact email a real address I read (Let's Encrypt sends expiry warnings there). This is the step that makes the whole "no open ports at home" design possible: with DNS-01, Let's Encrypt proves I own the name by checking a TXT record Stalwart writes to the zone through the provider from step 5. No port 80, no port 443, nothing reachable from outside required.

Why not the usual HTTP-01

HTTP-01 needs Let's Encrypt to fetch http://mail.22112002.xyz/.well-known/acme-challenge/... on port 80. That name will point at the VPS, which has no web server, and srv1 has no public port 80 either. TLS-ALPN-01 has the same problem on 443. DNS-01 is not a workaround here; it is the correct choice.

Checkpoint 6
  • The ACME provider saves. Certificates are requested per domain, so nothing is issued yet.

7. Add the domain

Directory › Domains → add 22112002.xyz. Two settings matter:

  • DNS management: Automatic, DnsServer = the Cloudflare provider. Stalwart will publish MX, SPF, DKIM, DMARC, SRV, MTA-STS, TLS-RPT, CAA and autoconfig records itself.
  • Certificate management: Automatic, ACME provider = the Let's Encrypt one. It will request a certificate for mail.22112002.xyz via DNS-01 and renew it on a schedule.

Then open the Cloudflare DNS dashboard in another tab and watch records appear. The domain object also has a read-only dnsZoneFile field showing exactly what Stalwart expects the zone to contain, which is the thing to compare against.

From this moment, mail to the domain changes behaviour

Stalwart publishes an MX record pointing at mail.22112002.xyz. That name has no A record yet; it gets one in part 08 when the VPS exists. Until then, anyone sending to @22112002.xyz gets a bounce or their server queues and retries for a few days. That is acceptable for me because nobody uses this domain for mail yet. If a domain already receives mail somewhere else, do this step and part 08 in one sitting, or set up the front door first.

DMARC: start at p=none

Part 03 explains DMARC. The short version: begin by asking receivers to report failures, not reject them. Check the DMARC record Stalwart published and make sure it says p=none with an rua= address that exists. Tighten to quarantine and then reject only after a few weeks of clean reports.

Checkpoint 7
  • dig +short MX 22112002.xyz returns mail.22112002.xyz. (with a priority number in front).
  • dig +short TXT 22112002.xyz includes a v=spf1 record and dig +short TXT _dmarc.22112002.xyz includes v=DMARC1.
  • A DKIM selector record exists: find the selector name in the domain's DNS view and dig +short TXT <selector>._domainkey.22112002.xyz returns a v=DKIM1 record.
  • Settings › TLS › Certificates shows an issued certificate for mail.22112002.xyz. If it's still pending, journalctl -u stalwart -f shows the ACME exchange and any DNS propagation wait.

8. Listeners: which port, on which address, for whom

This is where the architecture from part 05 becomes concrete. Stalwart can bind each listener to a specific address, and I'm using that deliberately. There are three audiences and each gets its own door.

Settings › Network › Listeners. The set I'm creating:

ListenerProtocolBindTLSPROXY protocolWho connects
smtpsmtp100.72.72.58:25STARTTLStrusted from <vps-tailscale-ip>HAProxy, part 08
submissionssmtp100.72.72.58:465implicittrusted from <vps-tailscale-ip>HAProxy, part 08
imaptlsimap100.72.72.58:993implicittrusted from <vps-tailscale-ip>HAProxy, part 08
imap-localimap127.0.0.1:143STARTTLSnoneRoundcube
submission-localsmtp127.0.0.1:587STARTTLSnoneRoundcube
httphttp127.0.0.1:8080none (Tailscale adds it)noneMe, via tailscale serve

Why the Tailscale IP and not 0.0.0.0

Binding to 0.0.0.0 means "every address this machine has": the LAN address, the Tailscale address, loopback. Then anything on my home network could talk SMTP to the server, and so could every other device in the tailnet. By binding the mail listeners to 100.72.72.58 only, the only machines that can even open a connection are tailnet members, and in part 08 the PROXY-protocol trust narrows the real traffic to the VPS alone. The bind address is the first firewall, before any password is checked.

About the PROXY protocol setting

Stalwart has a server-wide proxyTrustedNetworks list (Settings › Network › General) and a per-listener overrideProxyTrustedNetworks that replaces it for that listener. The three Tailscale-bound listeners will get the VPS's Tailscale IP in their override, so that HAProxy can hand over the real sender's IP (part 05). I don't know that IP until the VPS exists, so for now those listeners get created with the field empty and I come back to them in part 08. The loopback listeners must never have it set, because Roundcube does not send a PROXY header.

Verify at build time

Whether a listener with a trusted-proxy list set will also accept a plain connection without a PROXY header from that network. The docs describe the trust list but not the behaviour for a non-PROXY connection from a trusted address. Until part 08 I'm testing the Tailscale listeners from the laptop directly, which only works if either the list is empty or non-PROXY connections are tolerated. The checkpoint in step 11 settles it.

After saving listeners, the change needs a settings reload (there's a Reload action in the UI, or restart the service):

sudo systemctl restart stalwart
sudo ss -tlnp | grep stalwart
Checkpoint 8
  • ss shows exactly these binds: 100.72.72.58:25, 100.72.72.58:465, 100.72.72.58:993, 127.0.0.1:143, 127.0.0.1:587, 127.0.0.1:8080. No 0.0.0.0 or * lines belonging to stalwart.
  • From the laptop, nc -vz 100.72.72.58 993 connects, and nc -vz 10.0.0.10 993 (the LAN address, from a device on the LAN) does not.

9. Accounts

Directory › Accounts → add. Two to begin with:

  • olwethu@22112002.xyz, the real one, with a long password from the password manager.
  • test@22112002.xyz, a throwaway, so every test in this part sends between two mailboxes on the same machine and nothing leaves the house.

Stalwart supports app passwords (per-device secrets managed from the /account page). The plan is that the phone and Thunderbird each get their own in part 08, so revoking one device never means changing the main password. Roundcube uses the main login because it's on the same box and I type it anyway.

Checkpoint 9
  • Both accounts appear under Directory › Accounts with the domain 22112002.xyz.
  • Logging in to https://srv1.<tailnet>.ts.net/account as test@22112002.xyz works.

10. Roundcube, Caddy, tunnel

Everything in part 06, in order: PHP extensions, tarball to /var/www/webmail.22112002.xyz, database and schema, config.inc.php pointing at 127.0.0.1:143 and 127.0.0.1:587 with peer_name set to mail.22112002.xyz, Caddy block with explicit :80 and the private-path deny, cloudflared tunnel route dns homelab webmail.22112002.xyz, the ingress line, restart cloudflared, delete installer/.

sudo caddy validate --config /etc/caddy/Caddyfile && sudo systemctl reload caddy
sudo systemctl restart cloudflared
curl -I https://webmail.22112002.xyz

Then the moment that proves the home half: log in to https://webmail.22112002.xyz as test@22112002.xyz, send a message to olwethu@22112002.xyz, log out, log in as Olwethu, read it. That message went browser → Cloudflare → tunnel → Caddy → PHP → Roundcube → loopback SMTP 587 → Stalwart → mailbox → loopback IMAP 143 → Roundcube → back out the tunnel. Every component in this part was exercised, and the public internet carried nothing but HTTPS.

Checkpoint 10
  • curl -I https://webmail.22112002.xyz returns 200 (a Cloudflare 1033 means the tunnel is fine and nothing is listening locally; 502 from Caddy means PHP-FPM; check the socket name).
  • Login works for both accounts.
  • A message from test@ arrives in olwethu@'s inbox within seconds, and viewing its headers shows a DKIM-Signature line for d=22112002.xyz, proving signing is on even for local mail.
  • https://webmail.22112002.xyz/installer/ returns 403 or 404.

11. Testing the Tailscale doors directly

Roundcube proved the loopback listeners. The three Tailscale-bound listeners are what the VPS will use, and I want them proven before I pay for the VPS. From the laptop:

Is the certificate the right one?

openssl s_client -connect 100.72.72.58:993 -servername mail.22112002.xyz </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates

Expected: subject CN = mail.22112002.xyz, issuer Let's Encrypt, dates covering today. If the issuer is Stalwart's own self-signed fallback, the ACME step hasn't completed; check the journal.

Can I send through 465 with a login?

sudo apt install -y swaks   # on the laptop
swaks --to olwethu@22112002.xyz --from test@22112002.xyz \
      --server 100.72.72.58:465 --tls-on-connect \
      --auth --auth-user test@22112002.xyz \
      --header "Subject: swaks over tailscale"

swaks prints the entire SMTP conversation, which is the best way I know to see what part 02 describes: EHLO, the server's capability list, AUTH, MAIL FROM, RCPT TO, DATA, and the queued-message reply.

Does 25 answer like a real MX?

swaks --to olwethu@22112002.xyz --from someone@example.org --server 100.72.72.58:25 --tls

This is unauthenticated, like Gmail would be. Stalwart should accept it because the recipient is local. Try --to nobody@gmail.com too: that must be refused with a relay-denied style error. If it isn't, the server is an open relay and nothing else matters until that's fixed.

Checkpoint 11
  • openssl shows a Let's Encrypt certificate for mail.22112002.xyz.
  • Authenticated swaks on 465 ends with a 250 queued reply and the message appears in webmail.
  • Unauthenticated swaks on 25 to a local address is accepted; to an external address it is rejected.
  • Note for part 08: whether these tests worked with the PROXY trust list empty (expected) and what happens once it is set.

12. Backups, before there is anything worth losing

The whole server is two paths: /etc/stalwart/config.json (a few bytes saying where the database is) and /var/lib/stalwart/ (the RocksDB database: configuration, accounts, every message). Roundcube adds its MariaDB database and its config file. A nightly copy to somewhere that is not the same spinning disk is the minimum.

sudo tee /usr/local/sbin/backup-mail.sh >/dev/null <<'SH'
#!/bin/sh
set -e
DEST=/mnt/backup/mail/$(date +%F)
mkdir -p "$DEST"
systemctl stop stalwart
tar czf "$DEST/stalwart.tgz" /etc/stalwart /var/lib/stalwart
systemctl start stalwart
mariadb-dump roundcubemail | gzip > "$DEST/roundcube.sql.gz"
cp /var/www/webmail.22112002.xyz/config/config.inc.php "$DEST/"
find /mnt/backup/mail -maxdepth 1 -mtime +14 -exec rm -rf {} +
SH
sudo chmod 700 /usr/local/sbin/backup-mail.sh

Stopping the service for the few seconds the tar takes is the simple way to get a consistent copy of RocksDB; Stalwart also has its own backup and snapshot tooling in the UI, which I'll look at once the basics are stable. Where /mnt/backup actually points is the open question: the RAM-upgrade post already said an SSD is the next hardware step, and a second disk for backups is the same conversation.

Checkpoint 12
  • Running the script by hand produces the three files and systemctl status stalwart is running again afterwards.
  • A cron or systemd timer entry exists and journalctl shows it fired the next night.

13. Deliberately not done yet

If everything above passed, I have a working mail system that only I can reach. These are the pieces that make it reachable by the world, and they are all part 08 because they all need the VPS to exist first:

  • An A record for mail.22112002.xyz pointing at <vps-public-ip>, grey cloud.
  • A PTR record at the provider, mapping <vps-public-ip> back to mail.22112002.xyz.
  • HAProxy on the VPS forwarding 25, 465 and 993 to 100.72.72.58 with PROXY protocol v2.
  • The overrideProxyTrustedNetworks value on the three Tailscale listeners.
  • A Postfix relay on the VPS and a Stalwart Relay route so outbound mail leaves from the VPS's IP.
  • Confirming the SPF record Stalwart published covers the VPS IP (it uses mx, which will resolve to it once the A record exists).
  • The first real message to a Gmail address, and reading its headers.

Until then the domain receives nothing from outside, and that is by design: there is no point exposing a mail server to the internet before I've proven, privately, that it does what I think it does.

Glossary for this part

Bootstrap mode
Stalwart's first-start state when no config.json exists: web UI only on port 8080, a one-time admin password in the log, no mail services until the wizard finishes.
Checkpoint
A command whose output proves a step worked. The discipline of not moving on without one.
DNS-01
The ACME challenge where ownership of a name is proven by writing a TXT record, so no port needs to be reachable from the internet.
DnsServer / ACME provider
Stalwart's names for "credentials to edit a DNS zone" and "which certificate authority to ask, with which challenge". Domains point at both.
Bind address
The specific IP a listener accepts connections on. Binding to one address instead of 0.0.0.0 limits who can even connect.
overrideProxyTrustedNetworks
Per-listener list of proxies allowed to send a PROXY protocol header with the real client address. Set in part 08 to the VPS's Tailscale IP.
tailscale serve
Publishes a local port to the tailnet only, with HTTPS on the device's MagicDNS name. Used here for the admin UI.
swaks
"Swiss Army Knife for SMTP": a command-line tool that holds a full SMTP conversation and prints every line of it.
Open relay
A mail server that accepts mail for domains it doesn't host from anyone, unauthenticated. Spammers find them within hours. The 25-to-gmail test in step 11 checks for it.
